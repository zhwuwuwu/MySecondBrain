# LLM Agent Privacy：从敏感信息脱敏到全生命周期治理

> 研究问题：当个人 Agent 需要读取本地文件、调用工具、保存记忆并把部分内容发送给外部 LLM 时，业内通常如何保护隐私？是否需要按文件类型、业务领域分别处理？
>
> 当前实现：使用轻量语言模型判断本地文件中的敏感内容，将其替换为占位符后发送给大模型，再从返回结果中恢复。当前支持 DOC、CSV、Excel。
>
> 核心结论：**不应该为每一种文件类型重新做一套隐私识别模型，也不应该一开始为每个行业训练一套模型。更可扩展的路线是“格式专用解析器 + 统一中间表示 + 分层检测器 + 领域策略包 + 全链路数据治理”。**

## 1. 先回答两个问题

### 1.1 是否要逐个文件类型处理？

**需要逐个文件类型做解析和覆盖测试，但不需要逐个文件类型维护一套隐私判断逻辑。**

推荐架构：

```text
文件 / 消息 / 工具结果
        ↓
格式专用 Extractor
(DOCX / PDF / XLSX / CSV / OCR / Email / HTML / Code / Archive)
        ↓
统一中间表示 Canonical Representation
(文本、表格、单元格、结构、来源、位置、元数据、置信度)
        ↓
统一 PII / Secret / Domain Entity 检测
        ↓
策略决策：放行 / 脱敏 / 替换 / 阻断 / 人工确认
        ↓
发送给模型、输出处理、Memory/Cache/Log 治理
```

文件类型的差异主要在于“数据藏在哪里、如何还原、如何保留上下文”，而不是隐私概念本身不同。每个 Extractor 应负责完整发现内容，统一检测层负责判断内容是否敏感。

### 1.2 是否要逐个应用领域处理？

**需要领域策略包，但不建议一开始为每个领域单独训练完全不同的模型。**

可以分三层：

1. **通用层**：姓名、邮箱、电话、地址、身份证件、账号、IP、地理位置、凭证、API key、秘密等。
2. **领域层**：医疗 PHI、法律案件/当事人/特权材料、财务账户/卡号/交易、HR 员工信息、企业机密等。
3. **组织层**：本组织自己的客户号、项目代号、内部系统名、合同编号、专用字段和数据分类规则。

领域差异主要体现在：实体词汇、敏感等级、上下文、保留/遮蔽策略、谁可以解密和哪些场景必须阻断。模型能力可以共享，策略、词表、验证器和少量领域适配可以独立演进。

## 2. Privacy 的目标不是“把敏感词替换掉”

隐私保护至少要同时回答六个问题：

| 目标 | 问题 | 典型控制 |
|---|---|---|
| Data minimization | 这段数据是否真的需要送给模型？ | 字段裁剪、局部检索、摘要、最小上下文 |
| Detect | 哪些内容是个人数据、秘密、领域敏感信息？ | 规则、校验、NER、分类器、LLM judge、人工复核 |
| Transform | 发送前如何降低暴露风险？ | 删除、遮蔽、泛化、哈希、Tokenization、可逆伪名化 |
| Constrain | 谁能看到原文、映射表和模型输入输出？ | 本地处理、权限、密钥隔离、短期 token、租户隔离 |
| Retain | 结果会不会留在日志、缓存、Memory、训练集？ | 禁止训练、最短留存、删除/过期、访问审计 |
| Respond | 识别错误或发生泄露后能否恢复？ | 阻断、撤销、轮换、删除、回滚、事故证据 |

因此，“发送前脱敏”是重要控制，但不是完整 Privacy。还要考虑模型供应商是否保存输入、是否用于训练、输出是否重新暴露数据、Agent Memory 是否持久化、日志和 trace 是否包含原文，以及恢复映射表本身是否成为高价值秘密。

## 3. 当前“占位符替换”方案的评价

### 3.1 优点

- 在数据离开本地前建立了明确的 privacy boundary；
- 适合对外部模型不完全信任的场景；
- 可以保留任务结构，避免完全删除上下文；
- 如果占位符稳定，可以让模型在多处引用同一实体时保持一致。

### 3.2 主要风险

1. **只识别敏感词不等于识别敏感实体**：姓名、住址、案件事实、病历描述、合同内容可能没有固定关键词。
2. **小模型可能漏检或误检**：漏检造成隐私泄露；误检会损害任务质量。不能只用单一 LLM judge 做最终保障。
3. **占位符可能泄露语义**：`<VIP_CUSTOMER_001>`、`<CANCER_PATIENT>` 等标签本身就暴露敏感类别。
4. **映射表是秘密**：如果占位符可逆，原文—占位符映射表必须留在本地、加密、按任务隔离，不能进入模型上下文或普通日志。
5. **输出恢复可能扩大泄露**：模型可能把占位符放到邮件、代码、日志或不同语境中，恢复前要再次检查输出目的、收件人和数据流。
6. **跨文件一致性会泄露关联**：同一个稳定 token 在多个外部请求中复用，可能让服务方关联不同任务。稳定性应限定在单任务或明确授权的会话范围内。
7. **结构破坏**：把表格、公式、页码、段落和引用简单转成文本，可能让模型做出错误判断；隐私保护不能只追求脱敏率。

### 3.3 更稳妥的做法

- 默认优先**最小化数据**，能不发送原文就不发送；
- 对结构化字段先使用确定性规则和校验器；
- 对自然语言实体使用 NER/分类器，再用上下文模型补充；
- 高风险实体采用默认阻断或人工确认，而不是自动恢复；
- 使用任务级随机 token，例如 `<PERSON_7f3a>`，不要用真实类别和稳定全局 ID；
- 映射表、原文和 de-tokenization 服务保持本地并隔离；
- 输出恢复前检查数据用途、目标接收者、字段权限和是否发生新的外发；
- 对输入、脱敏后文本、模型输出、恢复后输出分别审计，但日志默认不保存原文。

## 4. 分层检测：不要只依赖一个模型

业内更常见的是检测器组合，而不是“敏感词表”或“一个大模型”二选一：

| 层 | 方法 | 擅长 | 局限 | 建议 |
|---|---|---|---|---|
| L0 | 文件元数据、来源和权限 | 文件来源、所有者、分类、是否允许外发 | 不识别正文敏感实体 | 作为第一道策略门 |
| L1 | Regex + 校验器 | 邮箱、电话、卡号、证件号、API key、连接串 | 对自然语言姓名和隐含语义弱 | 高精度结构化 PII 必跑 |
| L2 | NER / 轻量分类器 | 姓名、组织、地址、医疗/法律实体和上下文 | 领域迁移、歧义、语言覆盖 | 本地快速扫描和候选生成 |
| L3 | 上下文模型 / 小型 LLM judge | 判断“这段话是否构成敏感事实”、实体关系和语境 | 成本、延迟、不可完全确定 | 只处理候选或高风险内容 |
| L4 | 人工/组织策略 | 高风险、低置信度、法律/医疗/财务边界 | 成本高、不可完全自动化 | 作为阻断、解密和例外审批 |

没有一种方法能同时在所有实体上达到高 precision 和高 recall。规则对结构化 PII 强，NER 对人名/地名强，上下文模型对隐含语义强；生产系统通常组合它们，并分别测量漏检和误检。

## 5. 通用策略包与领域策略包

### 5.1 通用层应覆盖什么？

- 直接标识符：姓名、邮箱、电话、地址、身份证件、护照、驾照；
- 在线标识符：IP、设备 ID、Cookie、账号、位置；
- 认证材料：密码、API key、OAuth token、SSH key、云凭证、连接串；
- 财务通用实体：银行卡、账户、支付标识；
- 组织秘密：内部项目名、客户编号、合同编号、未公开代码和商业计划；
- 自由文本中的“可识别组合”：姓名 + 地址、病情 + 时间、账户 + 交易等。

### 5.2 领域包何时值得做？

当满足以下任一条件时，建议建立领域策略包：

1. 漏检或误检的代价明显高于通用场景；
2. 实体含义强依赖上下文，通用模型无法区分；
3. 行业有明确的数据分类、留存、披露或审批要求；
4. 需要不同的变换策略，例如财务字段保留数值统计，医疗记录保留临床关系但隐藏身份；
5. 客户有组织专用字段、编号和术语。

### 5.3 领域包的组成

领域包不一定是一个新模型，通常由以下内容组成：

- 实体类型和敏感等级；
- 词表、正则、校验器和上下文模式；
- NER/分类器或少量领域适配；
- 数据最小化和字段保留策略；
- 脱敏、泛化、伪名化、阻断和解密策略；
- 低置信度和例外处理；
- 标注集、回归集、漏检/误检阈值和审计规则。

## 6. 文件类型策略：解析器要专门化，隐私引擎要统一化

| 类型 | 必须检查的隐蔽位置 | 推荐处理 |
|---|---|---|
| DOC/DOCX | 正文、表格、批注、修订、页眉页脚、文档属性、嵌入对象、图片 OCR | 解析结构并保留段落/表格坐标；输出恢复要回写原结构 |
| PDF | 文本层、扫描页、图片、附件、元数据、隐藏文本、批注 | 文本抽取 + OCR；注意视觉顺序和扫描质量 |
| XLS/XLSX/CSV | 隐藏 sheet/行列、公式、批注、命名区域、元数据、单元格类型、编码 | 单元格级实体识别；保留表头、坐标、公式和类型；防止公式/CSV 注入 |
| 图片/截图 | OCR 文本、脸、证件、二维码、背景屏幕 | OCR + 图像隐私检测；图片遮挡或本地视觉模型处理 |
| Email/HTML | 正文、HTML 属性、链接、附件、签名、引用历史和隐藏内容 | 解析正文与附件；不要把外部链接内容默认为可信 |
| Code/Log | API key、token、连接串、路径、用户名、堆栈、业务数据 | Secret scanner + 结构化规则；避免把占位符写回可执行代码 |
| Archive | 内层文件、目录名、压缩包注释、嵌套压缩、恶意宏/对象 | 解包隔离、递归扫描、大小/深度/炸弹限制；未知类型默认不发送 |

**当前 DOC、CSV、Excel 的下一步不是复制三套模型**，而是补全解析覆盖、统一坐标和实体 schema，然后扩展 PDF/OCR、Email/HTML、Code/Log、Archive。

## 7. 脱敏变换的选择

| 变换 | 可否恢复 | 适合场景 | 风险 |
|---|---:|---|---|
| 删除/遮蔽 | 否 | 模型不需要该信息；高风险秘密 | 可能破坏任务可用性和上下文 |
| 泛化 | 否 | 只需要统计/范围/类别 | 仍可能通过组合信息重识别 |
| 哈希 | 通常否 | 去重、匹配、稳定比较 | 低熵值可被反查；不适合作为通用匿名化 |
| Tokenization | 是 | 需要模型保持实体一致性，且本地需要恢复 | 映射表、密钥和关联性必须保护 |
| Pseudonymization | 是 | 多文档任务、需要保留角色关系 | 仍是个人数据，不等于匿名化 |
| 加密/本地计算 | 视方案而定 | 极高敏感数据、不能暴露明文 | 成本、能力和模型可用性受限 |

如果输出必须恢复真实值，当前方案属于**可逆伪名化/Tokenization**，不应称为匿名化。可逆映射表仍是个人数据保护的核心资产。

## 8. Agent 全链路 Privacy 控制

### 8.1 发送前

- 先做权限检查、数据最小化和本地过滤；
- 只发送完成任务所需字段、片段和统计结果；
- 依据数据分类决定是否允许外部模型；
- 脱敏后重新扫描，确认没有原文、映射表或高风险组合残留。

### 8.2 模型调用中

- 选择有明确数据处理、留存、训练使用和区域承诺的模型服务；
- 为不同数据级别配置不同模型、租户、密钥和网络出口；
- 限制上下文、工具、Memory 和跨会话传播；
- 不把原文和去标识化映射表放入 system prompt、普通日志或工具参数。

### 8.3 输出后

- 扫描模型输出是否重新生成 PII、秘密或跨租户信息；
- 恢复 token 前检查输出目的、收件人、字段权限和动作风险；
- 外发内容需要单独审批，不能因为“输入已经脱敏”就自动放行；
- 对代码、CSV、HTML 等输出防止占位符残留和注入。

### 8.4 Memory / Cache / Log

- Memory 写入要有来源、任务 scope、可信状态、过期时间、删除和回滚；
- 缓存、trace、错误日志、评测数据和反馈集默认不保存原文；
- 记录“处理了哪类数据”和策略版本，必要时不记录数据值；
- 映射表按任务隔离、加密、短期留存，完成后销毁或按授权保留。

## 9. 推荐落地路线

### P0：把当前方案变成可审计的隐私边界

1. 明确数据分类：公开、内部、个人、敏感个人、秘密、领域高敏感；
2. 将小模型从“最终裁决器”改成候选发现器，并增加 Regex/校验器/NER 组合；
3. 建立统一 Entity schema：类型、位置、原文 hash、置信度、来源、策略版本、变换方式；
4. 任务级随机 token + 本地加密映射表 + 输出恢复前复检；
5. 记录漏检、误检、原文残留、token 残留和外发事件；
6. 对原文、映射表、模型输入、输出、Memory、日志分别做数据流盘点。

### P1：扩展格式和领域策略

- 补 PDF/OCR、Email/HTML、Code/Log、Archive；
- 保持统一隐私引擎，增加格式专用 extractor 和回写器；
- 先做医疗、财务、法律中风险最高且客户最明确的领域包；
- 用真实脱敏失败样本建立领域回归集，而不是先训练大模型。

### P2：做成 Agent Privacy 产品能力

- 用户可见的 Privacy Envelope：本次任务允许哪些数据离开本地；
- 按任务/工具/模型/地区动态选择数据策略；
- 本地优先、远程模型分级、敏感数据禁止外发；
- Privacy-aware RAG 和 Memory：检索前授权过滤，写入前分类，读取时按用户和任务 scope 过滤；
- 端到端数据流追踪和可证明删除/恢复。

## 10. 推荐评测指标

- Entity detection precision / recall / F1，按通用层和领域层分别统计；
- 原文残留率、敏感组合漏检率、错误遮蔽率；
- Token 一致性、token 残留率、错误恢复率；
- 任务质量：结构保留、公式正确、引用关系、摘要质量；
- 不同文件类型的覆盖率和解析失败率；
- 模型、工具、Memory、日志和缓存各出口的明文暴露率；
- 跨任务/跨租户关联率；
- 高风险数据的人工审批覆盖率、阻断率和误阻断率；
- 删除请求后的残留时间和可验证删除率。

## 11. 最终建议

对你们当前实现，最合理的判断是：

> **保留“本地识别 → 本地替换 → 外部模型处理 → 本地恢复”的核心方向，但把它升级为格式无关的隐私引擎。文件类型由 Extractor 适配，领域由策略包适配，检测由规则/NER/上下文模型分层完成，最终由数据最小化、访问控制、输出复检、Memory/Log 治理和审计闭环兜底。**

不要一开始为 DOC、CSV、Excel、医疗、法律、财务分别训练六个模型。先统一实体 schema、数据流和评测框架；只有在某个领域的漏检代价、规则差异和客户需求足够明确时，再增加领域词表、验证器或小型适配模型。
