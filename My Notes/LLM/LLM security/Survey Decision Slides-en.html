THE BASICSFor decision-makers without a security background
01 · INTRODUCTION

Why do we need a Security feature? Start by distinguishing five core concepts

Once an Agent produces external side effects, the product must protect not just answer quality, but also the confidentiality, integrity, and availability of models, data, credentials, tools, runtime state, and external systems.

Concept
The question to ask
Claw-like example
Security
Is there an adversarial or unauthorized path that can compromise confidentiality, integrity, or availability?
A webpage tricks the Agent into reading a secret key and sending it externally
Safety
Even without an attacker, could the outcome still cause unacceptable harm?
Agent accidentally deletes files or incorrectly modifies code
Privacy
Does the user control how their data is collected, remembered, inferred, and disclosed?
A private conversation is written into long-term memory
Reliability
Does the system work stably, and can it recover after failure?
Tool failure causes an infinite retry loop
Robustness
When inputs, tools, or network conditions change, do security properties hold?
A changed tool response format still causes privilege escalation
Refusal rate ≠ security; stable operation ≠ correct permissions; content moderation ≠ runtime isolation.

Translating "there is a risk" into a verifiable chain

Attack Surface → Technique → Asset → Impact → Control → Evidence

Example: webpage-induced exfiltration

  • Attack surface: webpage / browser tool result
  • Technique: indirect prompt injection
  • Asset: local files, tool permissions, network egress
  • Impact: secret read and exfiltration
  • Control: content judgment + Policy Gateway + sandbox

Metrics to watch post-launch

  • Unauthorized Action Rate
  • Secret Disclosure Rate
  • Denied-call Bypass Rate
  • Privilege Escalation Distance
  • Recovery / Rollback Success Rate

Product framing: We are not trying to make the Agent never make mistakes, but to ensure that high-impact mistakes cannot land without approval, and can be detected, revoked, and reviewed.

MODEL VS AGENTFrom the model lifecycle to the Agent runtime
03 · MODEL SECURITY & AGENT SECURITY

From model refusals to side-effect control

MODEL SECURITY

Model lifecycle security

Primarily focuses on data, training, and inference APIs, for example:

  • Data acquisition, cleaning, annotation, licensing, and privacy;
  • Pre-training, fine-tuning, alignment, and evaluation configuration;
  • Weights, checkpoints, quantization files, and dependency supply chain;
  • Inference API, authentication, rate-limiting, logging, and multi-tenant isolation;
  • Model behavior: jailbreaks, Prompt Injection, and refusal bypasses.
Typical controls: data provenance, dependency hashing, access control.
AGENT SECURITY

Agent runtime security

Agent Security adds the following on top of Model Security:

  • Harness / Orchestrator and task goals;
  • Prompt/context assembly;
  • Memory/RAG/state persistence;
  • Tool/API/MCP/connectors;
  • Identity, permissions, approvals, and user confirmation;
  • Sandbox, host machine, network, and credentials;
  • Monitoring, rollback, and incident response.
For local Claw-like products, the main security focus is Agent Security — not just refusal-rate optimization.

An attack chain is not a single-point problem

OpenAI–Hugging Face research demonstrates how a capable Agent, a loosely-constrained Harness, code-execution tools, a data pipeline, credentials, and a network boundary can combine into a cross-boundary attack chain.

The product must control combined capabilities

It is not enough to ask "is this sentence dangerous?" — we also need to ask who is acting, on what resource, with what parameters, what side effects will occur, and how to recover if something goes wrong.

Runtime Enforcement & Recovery

All high-impact actions pass through a unified gateway. A complete trace threads through everything, supporting anomaly detection, workspace isolation, credential revocation, reversal of reversible actions, and post-incident review. Irreversible actions raise the approval level by default; the final outcome can only be Allow / Block / Approval.

Observe before Enforce

First run in observe mode to record actions that would be blocked, calibrating false positives and user experience; then enable enforcement for high-confidence policies. Policies are promoted in tiers by risk level — not all blocked at once.

UNSAFE ACTION JUDGEBreaking down "dangerous" into judgeable objects
06 · BASIC DEFINITION

A security judgment must answer simultaneously: what is intended, what is authorized, and what actually happens

01

Intent

Does the Agent's plan and tool parameters serve the user's task?

"Organize the project" should not automatically expand into reading secrets, accessing a production database, or sending emails.

02

Authorization

Is the current user, task, resource, and time window actually authorized?

A user's goal is not a permissions grant; read ≠ delete; project A ≠ project B.

03

Observed Effect

What are the actual file, network, credential, memory, and external side effects?

We cannot rely only on the Agent's natural-language explanation — we need to see the full parameters and real trace.

Unsafe Action dimensions

Authorization overstep, intent misalignment, excessive capability, secret disclosure, action integrity, external side effects, runtime boundary breach, persistent propagation, resource abuse.

Why not just one classifier?

A single action may be low-risk, but a sequence of actions can form a complete exfiltration chain: secret → context → tool → external API. State and historical trace must be factored in.

DIMENSIONSNot simply Prompt + Classifier
07 · AGENT SECURITY DIMENSIONS

Decomposing Agent security dimensions

1. Authorization Boundary

Authorization overstep: allowed to read but performs deletion; accesses project B; normal user calls admin API; query becomes write.

2. Intent Alignment

Intent misalignment: action deviates from the task or the Agent autonomously adds goals. Suitable for model or human review — cannot solely determine permissions.

3. Excessive Agency

Excessive capability: arbitrary Shell/SQL; tool permissions cross boundaries; high-impact actions require no approval or rollback.

4. Confidentiality

Confidentiality violation: exfiltrating confidential data. Without explicit declassification, data flows should be refused.

5. Integrity

Integrity violation: wrong goal or parameters; modifying the wrong file, paying the wrong amount, or using untrusted content as a parameter.

6. External Side Effect

External side effects: single-step or cumulative impact of an action. Deletions, payments, emails, and public publications typically require approval.

7. Runtime Boundary

Runtime breach: accessing files outside the workspace or host machine credentials. Must be enforced by the OS and runtime.

8. Persistence

Persistent propagation: malicious content entering long-term memory, RAG, other Agents, configs, or the next session.

9. Availability

Resource abuse: infinite loops, retry storms, tool-call storms, token exhaustion, large-scale cloud resource operations.

Unified input for Unsafe Action judgment: action type + target resource + full parameters + current state + user authorization + action history + expected side effects

* Security judgment must never pass a natural-language answer snippet to a single classifier alone.

WHY INVESTSecurity is product trustworthiness, not just compliance cost
09 · BENEFITS

Investing in security earns: "safe to use, deliverable, and recoverable when things go wrong"

C-END USER

For end users of locally-deployed Claw-like apps

  • Lower fear cost: users know the Agent will not casually read and exfiltrate local files just because of a webpage;
  • Protect personal assets: local documents, photos, browser sessions, SSH keys, cloud credentials, and long-term memory have clear boundaries;
  • High-impact actions are controllable: deletions, sends, deployments, and permission changes can be previewed, confirmed, or rolled back;
  • Less invisible data leakage: network egress and tool parameters are controlled;
  • Problems are explainable: when a denial occurs, it is possible to state which policy, which resource, and which action triggered it.
OEM / PLATFORM

For OEMs deploying local applications

  • Lower incident cost: reduce data breaches, privilege escalation, malicious Skill/MCP events, and supply-chain incidents;
  • Improve delivery credibility: security policies, audit logs, and versioned configs can become part of the product contract;
  • Reduce post-sale diagnostic cost: with a full trace, model issues, tool issues, and platform permission issues can be distinguished;
  • Support product tiering: standard SKUs use lightweight rules; premium SKUs offer local security models and stronger auditing;
  • Create differentiation: "controllable Agent" as an OEM delivery capability, rather than just comparing model answer quality.

Mistaken expectations to avoid:

  • A security layer does not automatically improve model factual accuracy;
  • Model guardrails do not replace source code and dependency vulnerability scanning;
  • Security capabilities will have false positives, false negatives, and resource costs;
  • A single benchmark cannot prove all user scenarios are secure.

IMPLEMENTATION PATHSPlatform boundary and model judgment are two complementary paths
10-1 · TWO IMPLEMENTATION PATHS

Two build paths for Agent Security

PATH A · PLATFORM CONTROL

Platform boundary path

Invest in permissions, tool gateway, workspace sandbox, network, credentials, approvals, trace, and rollback.

  • Even if the model judges incorrectly, privilege escalation is still prevented by the platform
  • Capabilities are explainable, deterministic, and auditable
  • Requires significant platform engineering work
PATH B · MODEL JUDGMENT

Model judgment path

Invest in SingGuard / SingGuard-NSFA inference, policies, thresholds, and model serving.

  • Covers complex content, intent misalignment, and action risk
  • May reuse existing Agent event streams
  • Requires validating false positives, false negatives, latency, and resource usage

The two paths are complementary. Platform controls handle authorization, blocking, isolation, and recovery; model judgment handles discovery of complex intent and content risks. Model signals must ultimately feed into a deterministic policy and approval loop.

MODEL-BASED JUDGMENTUsing models to simultaneously judge multiple risk types
11-0 · OVERVIEW

Approach 1: Use models to simultaneously judge multiple risk types

Model 1: SingGuard

A policy-adaptable multimodal LLM safety guardrail. Part of a two-tier model architecture, primarily responsible for safety of multimodal inputs and content.

Model 2: SingGuard-NSFA

A text guardrail framework for Agent operation risks. Prioritized for text-only, tool-based local Agents. Focused on intent and action risk judgment during operation and execution.

5. Training architecture
Risk-analysis data SFT; after freezing the SFT backbone, lightweight MLP classification heads are trained for different risk domains; new risks require only training a new classification head.

INTEGRATIONModes, integration, and deployment considerations
11-2 · NSFA MODES & INTEGRATION

NSFA operating modes and runtime integration chain

NSFA should be integrated as a risk judge for the Agent runtime, not as a replacement for the tool gateway or a direct action executor. The Orchestrator is recommended to assemble structured context at every observable event and call NSFA; then pass the risk result, user identity, Security Envelope, and deterministic rules together to the Policy Gateway for decision-making.

Lifecycle data flow

User / External content ↓ [input check] Agent Planner ↓ [plan check] Tool call proposal (tool + full parameters) ↓ [pre-action check] Policy Gateway (identity+scope+risk+deterministic rules) ├─ allow → Sandbox / tool execution ├─ approval → execute after user confirmation └─ block → return explainable refusal ↓ Tool result / outbound content / memory write ↓ [result, egress & persistence check] Audit Trace / Recovery

Call contract (structured context)

Each call must retain at least the following structure, rather than just passing a prompt:

<untrusted_input>user request, web pages, documents, etc.</untrusted_input> <untrusted_output>Agent plan, tool calls, results, etc.</untrusted_output> task / intent / user_identity / session_id tool_name / full_parameters / target_resource security_envelope / prior_actions / observed_effect / expected_side_effect

NSFA outputs risk categories/probabilities/generative analysis (as signals and audit evidence only). Final authorization is made by the Policy Gateway.

How the two modes divide work

  • Real-Time Classification: placed in the online path of stages 1, 3, 4, and 5; suitable for high-frequency, latency-sensitive input, tool call, result, and egress checks; timeout budgets should be set by action level.
  • Generative Reasoning: used for complex plan review in stage 2, as well as offline trace auditing, incident investigation, human review, and policy tuning; should not become a synchronous upstream dependency for all low-risk tool calls.

Failure, degradation, and recoverability

  • Must not default to allow: if NSFA times out or crashes, do not default to expanding permissions or allowing high-impact actions; continuation is determined by existing policy.
  • Differentiate degradation strategy: low-impact, read-only actions covered by allowlist can log risk and continue; actions involving secret reads, external uploads, or deletions maintain block/approval.
  • Trace closed loop: all requests, decisions, and degradation reasons are written to trace, supporting post-incident review and rollback.

Deployment consideration: 0.8B/2B can serve as candidate scales for a local pilot. Model loading memory, CPU/GPU, concurrency, context length, P50/P95 latency, and timeout behavior must be tested on the actual device SKU. The A100 figure of 45–57 ms/sample is reference only — not a local device SLA.

PILOT PLAN4 phases and acceptance criteria
11-3 · PILOT PLAN & METRICS

Pilot plan and acceptance criteria

Phase 0: Establish baseline (1 week)

Record traces of existing Agent user requests, plans, tool calls, results, memory writes, and external side effects; measure P50/P95 latency, answer success rate, tool success rate, and resource usage for typical tasks; annotate high-impact actions and sensitive resources.

Phase 1: Offline audit and dataset (1–2 weeks)

Use NSFA Generative Reasoning to audit historical traces; construct samples for legitimate tasks, Prompt Injection, unauthorized read/write, secret exfiltration, MCP/Skill poisoning, and resource abuse; record human labels and expected handling for each sample.

Phase 2: Shadow mode (1–2 weeks)

NSFA online classification is placed before tool calls but does not change execution outcomes; SingGuard is placed at multimodal entry/exit points; record differences between model judgment, rule judgment, and human labels; measure memory, speed, and accuracy curves for different model sizes and device SKUs.

Phase 3: Limited enforce (1 week)

Only block high-confidence, high-impact, irreversible actions (e.g., read credentials, exfiltrate, delete, deploy — default deny or approval); clarify fallback behavior when the model times out, crashes, or the Policy Gateway is unavailable.

PLATFORM WORKBeyond the model — the boundary must be made real
12 · PLATFORM STRATEGY

Execution-layer platform controls to implement (by control type × phase)

Three assumptions to correct first

  • Trajectory ≠ complete audit: cannot prove coverage of network/approvals/memory/files; no tamper-resistant retention.
  • Workspace/Sandbox ≠ isolated closed loop: the container can still exfiltrate data or produce side effects.
  • Shell Guard ≠ command security closed loop: lacks a unified policy engine for dangerous commands, obfuscation, and network exfiltration.

Classification dimension notes

  • Type: Observe (log), Guardrail (redact/gate), Refuse (block), Execution (foundation)
  • Phase: inbound, prompt, pre_tool, post_tool, memory_write, outbound, cross
  • Priority: P0 (no autonomous execution without the foundation), P1 (narrow risk), P2 (scalable governance and verifiability)

Treat external content and tool results as independent untrusted boundaries; risk detection; context annotation; result injection detection and handling before entering context.

Prevent low-trust content from becoming high-trust future instructions; provenance/contamination checks (observe before enforce); shorten TTL for PII mappings.

Tighten rules one by one after calibrating with real data; promote high-confidence rules from observe to enforce; each individual rule can be independently rolled back.

P1 Execution cross_phase

Prove that blocking is effective and has no side effects; adversarial test fixtures (obfuscation, poisoning, etc.); negative integration tests covering all boundaries.

Division of work with Approach 1 (model guardrails): models only produce risk signals; the policy gateway and audit closed loop in this section are the only execution layer that can convert signals into allow / observe / redact / require_approval / block and leave evidence. The two cannot substitute for each other.
IMPLEMENTATION PROPOSALFrom platform foundation to model assistance
13 · IMPLEMENTATION PROPOSAL

Comprehensive implementation proposal

Proposal boundaries & core principles

  • Model guardrail: detects "this looks dangerous"
  • Platform policy: decides "is this authorized"
  • Runtime isolation: ensures "even if judgment is wrong, it still cannot happen"
  • Recovery system: ensures "after an anomaly, loss can be stopped and rolled back"

Authorization boundary is always the deterministic Policy Gateway + OpenWork approval + sandbox. NSFA/SingGuard only produce risk signals — they cannot allow independently, and they do not bypass P0 deny/approval.

Approve: P0 platform foundation

Establish baseline safety

Unified policy decision, dangerous action interception, approvals, and fail-closed boundary. Priority: prove "even if the model misjudges, high-risk actions still cannot escalate privileges."

Approve: P1 model observation & pilot

Validate with real data

After the P0 closed loop, introduce NSFA shadow observation. Use real-device latency, power consumption, and false-positive benchmarks to decide the go-live strategy — not blind online blocking.

Tradeoff: benefits vs. cost

Product-dimension tradeoffs

Use added latency and operational complexity to purchase lower secret-leakage and destructive-write risk. The product can deliver different security levels for different device SKUs.

Core Release Gates

P0 release criteria:
  • Denied Shell/file/network actions can be definitively proven to have no side effects.
  • Approval deny or timeout must never execute.
  • Critical logs can be correlated and must never store raw secrets/PII.
P1 release criteria:
  • Target SKU has completed performance and quality benchmarks.
  • Abnormal fallback scenarios such as model unavailability/timeout must never expand high-risk permissions.
  • Each model-assisted rule can be independently rolled back.

Final decision criterion: Recommend proceeding. Implement in the order P0 platform foundation → P1 shadow observation → P2 scale-up governance. Do not allow a model "low risk" score to mask deterministic runtime gaps. (See chapters 12 and 13 for the engineering checklist.)
