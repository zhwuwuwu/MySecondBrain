# 长 Agent System Prompt 的跨模型可移植性：现状与研究缺口

> 范围：不同于 [[3. Adaptive prompt for diff LLM]] 及其精读笔记（[[3.1. Cross-Model Prompt Transfer 深度解读]] 等）讨论的"短任务指令跨模型迁移"，这里专门研究**生产级 LLM 编码 agent 的完整 system prompt**（定义角色、可用工具、工作方法论、输出格式，常见 1000-20000+ token）能否/如何跨模型（Claude↔GPT↔Gemini↔开源模型）保持行为等价。
> 结论先说：**这是一个真实存在、目前没有被学术界系统研究的空白**，但空白周围已经有相当多的间接证据和工业界实践可以借鉴。

---

## 0. TL;DR

1. **规模不是一个量级**：生产级 agent system prompt 实测 2,300–22,500 token，比学术界"跨模型 prompt 迁移"论文常用的 <500 token 规模大 **5–50 倍**（PromptBridge 等论文实际优化的也只是几百 token 的任务包装层，见第 2 节）。
2. **"按模型分版本"是行业默认做法，不是例外**：OpenCode、Codex CLI、Cursor、Claude Code 都有实锤证据证明存在按后端模型分发不同 system prompt 的机制，且差异是功能性的（工具名、控制结构、思考预算都不同），不是措辞上的 paraphrase。
3. **没有论文直接研究这个问题**，但至少 6 篇 2026 年的新论文从不同角度擦边——interference 审计（Arbiter）、harness 组件分解（Agentic Harness Engineering）、system prompt 泛化性差（Sprig）、skill 可移植性（SkCC）、frozen playbook 迁移条件（"When Do Prompt-Side Agent Playbooks Transfer"）、model×scaffold 联合鲁棒性（"A Jagged Frontier"）——拼起来能看清问题形状，但没有一篇给出方法论。

---

## 1. 真实 agent system prompt 到底有多长、长什么样

数据来自 [jujumilk3/leaked-system-prompts](https://github.com/jujumilk3/leaked-system-prompts)、[x1xhlol/system-prompts-and-models-of-ai-tools](https://github.com/x1xhlol/system-prompts-and-models-of-ai-tools)（143K★）、[elder-plinius/CL4R1T4S](https://github.com/elder-plinius/CL4R1T4S)（50K★）等泄露/抓包收集的真实生产 prompt。

### 1.1 长度实测（仅 system prompt 文本，不含工具 JSON schema）

| 工具 | 字符数 | 词数 | 约 Token | 工具定义数 |
|---|---:|---:|---:|---:|
| **OpenCode** | 10,509 | 1,621 | ~2,300–3,500 | 11 |
| **Cursor Agent v1.0**（Claude Sonnet 4） | 9,106 | 1,448 | ~2,400 | — |
| **Anthropic Claude Code** | 23,249 | 3,476 | ~5,200–7,750 | 35 |
| **OpenAI Codex CLI** | 24,275 | 3,662 | ~5,400–8,100 | 9 |
| **Cursor 2.0** | 23,810 | 3,790 | ~5,300–7,950 | 多个 |
| **Cursor Agent v1.2**（GPT-4.1） | 32,765 | 5,343 | ~8,700 | 多个 |
| **Windsurf Cascade** | 34,725 | 4,952 | ~7,700–11,600 | 多个 |
| **Replit Agent** | 32,754 | 4,453 | ~7,300–10,900 | 多个 |
| **Cline** | 48,063 | 7,354 | ~10,700–16,000 | 15+ |
| **Devin** | 51,508 | 8,202 | ~11,500–17,200 | 命令式 |
| **v0** | 67,499 | 8,421 | ~15,000–22,500 | 多个 |

最小的（Cursor Sonnet 4 变体）约 2.4K token，最大的（v0）约 22.5K token，**跨度约 10 倍**。而学术界跨模型 prompt 可移植性论文（PromptBench、DSPy 优化器、指令归纳类基准）通常研究 <500 token 的 prompt——**规模差距约 5–50 倍**。

### 1.2 结构骨架高度一致

八个被调研的工具都出现同一套结构骨架的大部分或全部：**(a)** 角色/人设定义、**(b)** harness/运行环境描述、**(c)** 工具列表+逐工具使用策略、**(d)** 工作流/方法论规则、**(e)** 输出格式规则、**(f)** 安全/约束条款、**(g)** 可选的 few-shot 示例。

值得注意的细节：
- **工具是 prompt 的一部分，但不计入上表长度**——Codex CLI 带 9 个工具定义、Claude Code 带 35 个、OpenCode 带 11 个、Cline 带 15+ 个，这些以 JSON schema 形式随 system prompt 一起送入模型，会让实际"conditioning signal"比纯文本长度更大。
- **多数工具混合 zero-shot 指令与 few-shot 示例**——OpenCode 内嵌 `<example>` 块讲代码引用格式，Replit 有 `<example_output_format>`，Codex CLI 有整节"Reference examples"，学术文献通常把这两类研究问题分开处理，产品实践里它们是同一个文件。
- **Harness 上下文在请求时追加**——工作目录、环境变量、scratchpad、session memory 都会在运行时拼进 system prompt，意味着"system prompt 长度"是下限，不是总量。

## 2. PromptBridge 等现有跨模型工作实际覆盖的是哪个规模——不是这个规模

专门核实了 [[3.1. Cross-Model Prompt Transfer 深度解读]] 里最核心的 PromptBridge（arXiv 2512.01420）在 SWE-Bench Verified / Terminal-Bench 上到底优化的是什么：

**结论：不是长 system prompt，是套在现成 agent 框架外面的一层短任务包装。**

- SWE-Bench Verified 用的是现成的 **`mini-SWE-agent`** 框架，Terminal-Bench 用的是现成的 **`Terminus`** 框架——论文原话（§5.2）："For SWE-Bench, we utilize the framework of mini-SWE-agent. We use the Terminus framework for evaluation on Terminal-Bench."
- PromptBridge 优化的只是 Appendix E.3 里那段 **~800–1100 token** 的任务指令模板（角色定义"You are a senior software engineer..."+ 修改边界 + 代码质量要求 + 工作流 5 步 + 命令执行格式规则），后面拼接benchmark 提供的 `{{task}}`（具体 PR 描述）。
- **工具定义/shell 执行循环完全不属于被优化的文本**——由 mini-SWE-agent / Terminus 框架固定提供，PromptBridge 从不触碰。App B.4（MapCoder 多智能体设置）里也明确说"the default prompt is treated as the initial transfer point"，即用人工写的默认 prompt 当 source，同样不涉及工具schema 层。
- 所以 PromptBridge 报告的 +27.39%（SWE-Bench）/+39.44%（Terminal-Bench）增益，是"迁移一个 800-1100 token 的任务包装层"的增益，**不能直接推广到"迁移一个 1000-20000+ token、包含完整工具 schema 与多段工作流规则的系统提示"这个问题**——论文本身没有在这个规模上验证过。

## 3. 学术界目前最接近的工作（按相关度排序）

| 论文 | 核心发现 | 为什么没有真正命中你的问题 |
|---|---|---|
| **Arbiter: Detecting Interference in LLM Agent System Prompts**（arXiv 2603.08993，2026-03） | 把 Claude Code/Codex CLI/Gemini CLI 的 system prompt 当"软件工件"分析（245–1490 行），用多模型 LLM "审查员"找出 152 个问题 + 21 类干扰模式；成本 $0.27。**用跨模型评审当审计方法**——曾让 Google 修复了 gemini-cli 的一个真实 bug（[#16213](https://github.com/google-gemini/gemini-cli/issues/16213)）。 | 研究的是单个 vendor prompt **内部**的矛盾/冗余，跨模型评审只是审计工具，不是研究"这份 prompt 换个模型还好不好用"。 |
| **Agentic Harness Engineering**（arXiv 2604.25850，Fudan/北大/棋子智能，2026-04） | 把 agent harness 拆成 7 个可编辑组件（system prompt、工具描述、工具实现、middleware、skills、sub-agent 配置、memory）。固定模型演化 harness，Terminal-Bench 2 pass@1 从 69.7%→77.0%。**关键**：单独隔离优化 system prompt 反而是 **−2.3pp**，其他 6 个组件都是正收益（memory +5.6、tools +3.3、middleware +2.2）。跨模型迁移实验（§4.3）：在 GPT-5.4 high 上演化出的 7 文件 harness，无需重训直接迁移到 deepseek-v4-flash / qwen-3.6-plus / gemini-3.1-flash-lite 上获得 +2.3~+10.1 分。 | 研究的是"harness 整体"的可迁移性，不是"system prompt 单独"的可迁移性——但这个发现本身很重要：**它暗示 system prompt 可能恰恰是跨模型迁移链路里最脆弱的一环**，其他组件（尤其 memory/tools）比 prompt 本身更容易迁移。 |
| **Sprig**（arXiv 2410.14826，2024-10） | 系统性测试"为一个模型优化的 system prompt"在换模型/换尺寸后的表现："the larger gains for the original LLM do not carry over to new LLMs"——即优化后的 system prompt **不能**跨模型泛化。 | 只测 1-2 段的通用 system prompt（47 个任务），不涉及带工具/子agent 的长 agent prompt。 |
| **SkCC: Portable and Secure Skill Compilation**（arXiv 2605.03353，2026-05） | 研究跨框架（Claude Code / Kimi CLI / GPT）的 SKILL.md 可移植性，发现"不同 agent 框架对 prompt 格式的敏感度差异高达 40%"；skill 编译后 pass rate Claude Code 21.1%→33.3%、Kimi CLI 35.1%→48.7%，编译耗时 <10ms。 | 研究对象是**skill 文件**（通常远短于完整 system prompt），但框架假设完全一致："同一份 Markdown 应该在 Claude/GPT/Gemini/Kimi 上表现一致"——这正是长 agent prompt 场景需要被质疑的假设。 |
| **When Do Prompt-Side Agent Playbooks Transfer?**（arXiv 2608.05778，2026-08） | 在 ALFWorld / TAU2-Bench / XBench-DeepSearch 上研究"frozen playbook 迁移"，结论：**frozen 迁移只是一种有条件的冷启动方案，不是默认可靠的复用策略**——跨 runtime 迁移会导致重复查询、延迟停止、成本膨胀。 | 研究工具使用 agent 的 playbook（更像策略/流程描述），不是长 production 编码 agent 的完整 system prompt。 |
| **PragLocker**（arXiv 2605.05974） | 反向角度：试图**阻止** agent prompt 跨模型可用。测得未处理的 prompt 可移植性比率 ≈1.0（几乎总是"能跑"），注入噪声+代码符号锚定后可降到 0.2。 | 说明"能跑"（portable）和"跑得好"（preserved performance）是两件事——纯净的长 prompt 在任意模型上大概率不会报错，但性能是否等价完全是另一个问题，这正是你的问题。 |
| **A Jagged Frontier: Robustness of Code Agents**（arXiv 2608.18389，2026-08） | "没有一个模型鲁棒性排名能在所有 scaffold 上保持一致——Qwen 在 mini-SWE-agent 下最鲁棒，换到 OpenCode 下却最脆弱"。16 个（模型×scaffold×benchmark）格子里 6 个出现统计显著性能衰减。 | 证实了"鲁棒性是模型、scaffold、任务的联合属性"，直接支持"prompt 可移植性不能想当然"这个前提，但没有给出解决方案。 |
| **Same Model, Different Harness**（arXiv 2608.26218，2026-08） | 仅改变 harness（上下文窗口机制），SWE-bench Verified 上同一组冻结权重的 F2PF 从 28%→49%，完整解决方案从 43%→72%。 | 说明 harness/prompt 工程的影响可能**超过**换模型本身的影响，间接支持"迁移 prompt 比迁移模型更难"的直觉。 |

**综合判断**：把这几篇拼在一起能勾勒出问题的形状——(1) 长 agent prompt 存在真实的、可审计的内部质量问题（Arbiter）；(2) prompt 组件在 harness 里可能是最不容易迁移的一环（Agentic Harness Engineering）；(3) 已验证"为一个模型调优的 system prompt 不会自动泛化"（Sprig）；(4) 框架/scaffold 本身引入的方差可能比模型差异更大（Jagged Frontier、Same Model Different Harness）。但**没有一篇论文直接做"给定一个 Claude Code 量级的 system prompt，如何系统性地为 GPT-5/Gemini/开源模型生成等价版本"这件事**——这确实是空白，也是你之前提出的方向。

## 4. "按模型分不同 prompt" 是行业实锤，不是猜测

这是本次调研最直接、最有说服力的发现——不需要学术论文，产品代码和官方博客已经给出确定性证据：

### 4.1 OpenCode——7 个抓包捕获的变体
[OrcaReplay](https://github.com/Continuum-AI-Corp/OrcaReplay) 抓包捕获了 OpenCode 针对 7 个不同后端模型发出的、完全不同的 system prompt 文件。多数模型收到的模板彼此只差几十个字符，但 `gpt-5.6-sol` 这个变体**整个换了人设**——不再用 OpenCode 模板结构，直接是重写过的"deeply pragmatic, effective software engineer"人设，还带专属的 `multi_tool_use.parallel` 并行工具调用指令。OpenCode 自己也把这个能力暴露给用户，允许通过 `provider.systemPrompt` 覆盖。

### 4.2 Codex CLI——按模型代际瘦身
三个捕获变体：`gpt-5.6-luna`（20,855 字符）、`gpt-5.6-sol`（23,394）、`gpt-6-astra`（21,269）。第三方实测记录（[codex.danielvaughan.com](https://codex.danielvaughan.com/2026/04/19/three-terminals-meet-the-editor-cli-agents-vs-cursor/)）："Codex CLI 独特之处在于为每代模型准备单独的指令文件……针对微调模型的精简版本省了约三分之二的 prompt 文本，因为不用重新解释模型已经懂的工具。`model_instructions_file` 配置项可以整个替换掉 system prompt，本地模型用它能把开销从约 8500 token 降到约 3000 token。"

### 4.3 Cursor——工具名、控制结构、思考预算全不一样
4 个捕获的版本分别标注"powered by Claude Sonnet 4""GPT-4.1""GPT-5""Composer"。体积从 9K 到 40K 字符不等（3.5 倍差距）。独立逆向工程（[adiasg.com](https://www.adiasg.com/blog/comparing-cursors-prompts-across-models)）证实差异是**功能性**的：GPT-5 拿到 `apply_patch` + `edit_file`，Claude 拿到 `search_replace` + `write`；GPT-5 有专属的 `multi_tool_use.parallel`工具，Claude 没有；Claude 有 100 万 token 的思考预算，GPT-5 没有。Cursor 官方博客（[cursor.com/blog/codex-model-harness](https://cursor.com/blog/codex-model-harness)）直接确认这是设计决策："每个模型都需要针对性的指令和 harness 调整……OpenAI 团队与我们密切合作，让工具和 prompt 与 Codex CLI harness 对齐。"

### 4.4 Anthropic Claude Code——官方承认按代际减负 80%
Anthropic 工程博客（[claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)，2026-07-24）**直接承认**："我们为 Claude Opus 5、Claude Fable 5 这类模型移除了 Claude Code system prompt 里超过 80% 的内容，编码评测上没有可测量的质量损失。"旧模型的 prompt 里有"默认不写注释，不要写多段 docstring"这类具体规则，新模型的 prompt 换成一句"写的代码要像周围代码一样：匹配注释密度、命名习惯、写法"——**这是厂商第一方承认，同一产品对不同模型代际主动维护不同 system prompt**。

### 4.5 Cline——开源代码级实证
Cline 是开源的，调度逻辑直接可见：`anthropic.ts` 处理 cache_control 位置/1M上下文 beta header；`openai.ts` 按模型族（o1/o3/o4/gpt-5）切换 system→developer 角色、强制 temperature 为 undefined；`gemini.ts` 处理 Gemini 专属的 thinking-level 调度；对 `openai-codex` provider 直接返回 `undefined` 让指令走 in-band 而非 system role。**净效果**：即便发的是同一段文本，Cline 发给 Anthropic/OpenAI/Gemini/Deepseek 的实际 wire payload 结构也完全不同。

## 5. 对你研究方向的启示

1. **规模是第一道坎**：任何要研究"长 agent system prompt 跨模型迁移"的方法，必须先在 2K–20K token 规模上验证，而不是把 PromptBridge/MAPO 这类针对 <1K token 任务指令验证过的方法直接套用假设它能 scale。
2. **迁移单元可能不该是"整个 system prompt"**：Agentic Harness Engineering 的发现暗示，如果把 harness 拆成 7 个组件分别迁移，system prompt 可能恰恰是最难迁移、贡献最负的一块——这暗示一个可能更有效的切入点是"先确定 prompt 里哪些段落是模型无关的（角色/方法论），哪些是模型强相关的（工具调用格式、思考预算利用方式），分别处理"，而不是整体当一个黑盒去迁移。
3. **工业界已经用脚投票**：所有头部产品的解决方案都是"人工维护多份变体"，没有一家用自动化跨模型 prompt 迁移。这既说明问题的实际重要性（值得花人力维护），也说明目前没有足够好的自动化方案能替代人工——这正是这个方向"有研究价值、也有工程价值"的证据。
4. **可复用的评测基准是缺失的**：现有的 SWE-Bench/Terminal-Bench 类基准配的是"通用 agent 框架 + 短任务包装"（第 2 节），没有一个基准是"给定一个 Claude Code 级别的完整 system prompt，测它换模型后的行为保真度"——想认真做这个方向，第一步可能就是自建这样一个评测集。
