# Agent RL 的 Reward 设计与 Credit Assignment 深度解读

> 范围：展开 [[4. Agent RL & Self Evo]] 第 2.2 节“按 reward 分类”与第 2.3 节“按 credit assignment 粒度分类”的细节讨论——reward 从哪来、粒度怎么选，以及二者为什么必须一起设计。
> 主线问题：reward 设计不是“选一个打分器”，credit assignment 也不是“越细越好”；这篇笔记把两件事拆开讲清楚，再说明为什么最后必须合并考虑。

---

## 0. 两张总表（先看这里）

### Reward 来源对照

| 类型 | 信号从哪里来 | 优点 | 主要风险 | 典型 Agent 例子 |
| --- | --- | --- | --- | --- |
| **终局/结果奖励（ORM）** | 最终答案、任务状态、胜负 | 与最终目标直接对齐；定义简单 | 长任务中极稀疏，探索和 credit assignment 困难 | 网购是否买到目标商品、代码是否通过隐藏测试 |
| **过程奖励（PRM）** | 对中间 reasoning / turn / action 的打分 | 信号密、方差低、利于诊断 | judge 不准会把错误局部策略固化；可被"写得像正确步骤"欺骗 | 搜索查询是否相关、工具参数是否合理、子目标是否完成 |
| **程序化验证器** | 编译器、测试、状态机、数据库、浏览器 DOM | 可复现、可扩展，通常比语言 judge 稳定 | 只验证代理指标时会被钻空子；隐藏测试仍可能不足 | 单测通过率、SQL 执行结果、页面完成状态 |
| **偏好/LLM judge** | 人类比较、rubric、强模型评审 | 能覆盖开放式质量与多目标偏好 | position/length/style bias；judge 与被训模型同源时可能共谋 | 研究助理报告质量、客服回复帮助性 |
| **内在/探索奖励** | 新颖性、不确定性、信息增益、技能覆盖 | 稀疏任务中鼓励探索和发现 | 容易"为探索而探索"，与用户目标脱钩 | 未见 API、复杂游戏或开放世界中的状态覆盖 |

### Credit assignment 粒度对照

| 粒度 | action 单元 | 优点 | 代价/风险 | 更适合的场景 |
| --- | --- | --- | --- | --- |
| **Token** | 一个 token | 与自回归模型天然匹配；能微调语言形式 | 同一终局 reward 被复制到大量 token，噪声大且难解释工具因果 | 短答案、格式受控生成 |
| **Turn** | 一次完整 LLM response | 把 reasoning + tool call 视为 macro-action，训练接口较简单 | 一个 turn 内好坏混杂；长 turn 仍有归因误差 | 多轮 tool-use 的强基线 |
| **Step/tool** | 搜索、调用、代码执行、子目标 | 对应环境状态转移，可定位无效/危险 action | 需要定义 step 边界和局部 verifier；thought 与 action 的归因仍耦合 | API、浏览器、代码、数据库 Agent |
| **Trajectory** | 整条 episode | 与真实终局目标最一致，不要求局部标签 | 信号极稀疏、高方差、探索困难 | 高可信终局 verifier、短到中等 horizon |
| **层级（hierarchical）** | plan / option / low-level action | planner 管"做什么"，executor 管"怎么做"，可缩短有效 horizon | 需要可靠的子目标与 option 边界；错误 plan 会污染下层 | 长程任务、可分解工作流 |

带着这两张表读下面的展开讨论：reward 表回答“信号从哪来、会被怎么钻空子”；粒度表回答“在哪个尺度上给这个信号、代价是什么”。二者不能分开决策，第 3 节会说明为什么。

## 1. Reward 设计

### 1.1 先区分：reward 的来源、粒度与优化目标

一条 Agent 轨迹可写成 $\tau=(s_0,a_0,o_1,\ldots,s_T,a_T)$。奖励设计不是只选一个打分器，而是决定：

$$
R(\tau)=r_{\text{task}}+\lambda_p\sum_t r^{(p)}_t-\lambda_c C(\tau)-\lambda_s S(\tau)
$$

- $r_{\text{task}}$：最终任务是否达成；
- $r^{(p)}_t$：第 $t$ 步的过程信号；
- $C(\tau)$：成本，如 token、工具调用次数、延迟或金钱；
- $S(\tau)$：安全/约束违规的惩罚。

这里的公式是一个**设计模板**，不意味着实际系统必须线性加权。需要分别问清：奖励从哪里来、在何时给、能否被 agent 操纵、它是否真的与部署目标一致。

### 1.2 结果奖励与过程奖励的证据

**结果奖励**适合结果可验证的环境。DeepSeekMath 与 DeepSeek-R1 表明，规则化正确性/格式奖励可以支撑 reasoning RL；但它们的核心任务仍不同于带外部状态和副作用的工具型 Agent。参考：[DeepSeekMath (2024)](https://arxiv.org/abs/2402.03300)、[DeepSeek-R1 (2025)](https://arxiv.org/abs/2501.12948)。

**过程奖励**的核心前提是"局部好"与"最终好"高度相关。[*Let's Verify Step by Step* (2023)](https://arxiv.org/abs/2305.20050) 显示了过程监督在数学推理上的价值；迁移到 Agent 时，评分对象不应只看自然语言 thought，还应覆盖可执行 action、环境 observation 与状态变化。

### 1.3 程序化 verifier：最强信号也有边界

对于 Web、代码、数据库、游戏等环境，优先把**任务真实状态**编码为 verifier：

- 软件工程：补丁能否编译、测试是否通过、是否引入回归；
- Web：目标页面的 DOM/后端状态是否真的发生目标改变，而不是 agent 声称"已完成"；
- 数据库：返回值、写入状态、权限和事务约束；
- 工具调用：schema 合法性、参数类型、是否产生预期的状态转移。

这优于"LLM 读一下轨迹并给分"，但仍要防止 **proxy gaming**：若只奖励"测试通过"，Agent 可能修改测试；若只奖励"页面到达"，它可能绕过真实购买/提交语义。因此 verifier 需要：隐藏测试、不可由 Agent 修改的执行边界、对副作用的审计，以及与最终用户目标一致的状态谓词。可参考交互式环境设计：[WebShop (2022)](https://arxiv.org/abs/2207.01206)、[WebArena (2023)](https://arxiv.org/abs/2307.13854)。

### 1.4 LLM judge 与 preference reward：什么时候不得不用？

开放任务（研究、写作、复杂客服）没有唯一正确状态，常需 judge 或人类偏好。推荐将 judge 设计成**可执行 rubric**，至少分开评估：任务完成度、事实性/引用、约束遵循、可执行性、风险与成本；避免一个"总体好不好"的模糊分数。

实践上应做四类校准：

1. **成对比较与顺序随机化**：减少 position bias；
2. **长度归一或简洁性约束**：减少 verbosity bias；
3. **与小规模人工标注对照**：报告 judge-human agreement，而非只报告 judge score；
4. **对抗样本**：故意构造语气自信但事实错误、格式完美但未执行工具的轨迹。

RLHF 的偏好建模框架可作为背景参照：[InstructGPT (2022)](https://arxiv.org/abs/2203.02155)。但在 Agent 场景中，judge 最好评判**环境证据 + 轨迹**，而不只是最终文本。

### 1.5 Reward shaping 与 temporal densification

终局 $0/1$ reward 太稀疏时，可以加入中间信号，例如：

- 子目标完成：找到正确文档、获得有效 API token、定位可复现的 bug；
- action validity：工具名、参数、权限、调用顺序合法；
- progress：状态到目标状态的距离下降；
- efficiency：在成功前提下减少调用、token 和 wall-clock time；
- safety：越权、数据泄露、破坏性动作给大惩罚或直接终止。

但 shaping 的底线是：**它应帮助到达终局目标，而不能替代终局目标**。若只奖励"每一步都看似合理"，Agent 会学会冗长解释；若过度惩罚调用次数，Agent 会过早停止。较稳妥的顺序是：先建立可信终局 verifier，再增量加入少量、可消融的过程项；同时始终单独报告未加 shaping 的真实成功率。

### 1.6 Composite reward 的常见陷阱与实验设计

多目标 reward 常写成加权和，但权重 $\lambda$ 实际上定义了产品取舍。建议：

- 将**硬安全约束**（不可越权、不可破坏生产数据）放在环境/动作层拦截，而非只给软 penalty；
- 将"成功率"和"成本"分别报告，避免一个总分掩盖 trade-off；
- 对每个 reward component 做消融，检查性能来自任务能力还是投机利用某个子项；
- 检查 train reward 与 holdout、人工评估、真实状态成功率的相关性；
- 保存完整 trajectory，人工审计高分失败与低分成功样本。

> 一个实用原则：**能由环境确定性验证的部分，不要交给 LLM judge；必须用 judge 的部分，不要让它单独决定任务成功。**

## 2. Credit Assignment 粒度

### 2.1 问题的精确定义

Credit assignment 问的是：得到最终回报 $R$ 后，**哪些过去的决策应得到多少正/负更新**。对第 $t$ 个决策，policy gradient 常通过 advantage 进行更新：

$$
\nabla_\theta J \approx \sum_t \nabla_\theta\log\pi_\theta(a_t\mid s_t)\,A_t,
\qquad
A_t=G_t-V(s_t)
$$

其中 $G_t$ 是从 $t$ 往后的 return，$V(s_t)$ 是 baseline。难点不在公式本身，而在 Agent 中：$a_t$ 可以是一段数百 token 的 response、一次工具调用或一个子计划；$s_t$ 只是部分可观测的上下文；终局 reward 可能在几十轮之后才出现。

### 2.2 粒度并非"越细越好"：以修复 bug 为例

以"修复一个 bug"为例：Agent 先搜索代码、再阅读文件、编辑补丁、跑测试、提交结果。若测试失败，trajectory-level 方法只能说"整条轨迹不好"；step-level verifier 可以指出"搜索结果不相关""编辑未通过编译"还是"测试选择错误"。但若补丁最终通过所有隐藏测试，前面看似绕路的搜索也可能是必要探索——因此不能机械地把每个局部失败都当作负 reward。

### 2.3 从稀疏终局 reward 到中间 credit 的四条路线

1. **学习 value / advantage baseline**：用 $V(s_t)$ 预测从当前状态成功的概率或未来 return，再用 $G_t-V(s_t)$ 降低方差。GAE 是经典 bias–variance 折中工具：[Generalized Advantage Estimation (2015)](https://arxiv.org/abs/1506.02438)。
2. **过程 reward model（PRM）或局部 verifier**：为 turn/step 产生中间 reward，直接 densify 信号。风险是 PRM 的偏差会系统性改变优化目标。
3. **Reward redistribution**：将终局 reward 根据"何时出现了决定性信息"重新分配到较早步骤，而不只是平均摊给所有 token；此思路的 RL 原型见 [RUDDER (2019)](https://arxiv.org/abs/1806.07857)。
4. **反事实/差分 credit**：比较"有该 action"和"替换/移除该 action"后的 outcome，近似其边际贡献。多 Agent 的 COMA 用 counterfactual baseline 分离各 Agent 对共享回报的贡献：[COMA (2017)](https://arxiv.org/abs/1705.08926)。单 Agent tool-use 中也可用 replay、action ablation 或 simulator 做近似，但成本通常很高。

### 2.4 Turn-level 为什么是常见折中？

一个 Agent turn 往往同时输出 reasoning、决定是否调用工具、填参数，并得到 observation。把这个闭环作为 macro-action 有三点好处：

1. 环境只需在 turn 边界 reset/record，工程实现和并行 rollout 更可控；
2. 工具 observation 能进入下一状态，符合实际交互语义；
3. 相比 token-level，reward 不会在长文本中被无意义地重复广播。

它的代价是：模型可能在同一 turn 中产生很长的错误推理后又给出正确 tool call，或反之；同一个 advantage 更新会同时强化两者。可用更短 turn、结构化 action（thought / tool / final 分段）或在关键 action 上加 verifier 来缓解。

### 2.5 Step/tool-level：最适合真实工具环境的接口

建议把可执行 action 显式结构化，例如：

```text
state: 目标 + 已观察到的页面/代码/数据库状态
action: {tool_name, arguments}
observation: 工具返回 + 可信状态摘要
local checks: schema valid? permission valid? state changed as expected?
```

这样可以对"调用无效 API""参数类型错误""重试同一失败调用""写入了错误表"等事件给出局部 credit。但不要把自然语言 thought 当作可靠的因果解释：真正应优先归因的是**环境可观察的 action 和状态转移**。ReAct 将 reasoning 与 acting 交替呈现，是理解这一接口的有用起点：[ReAct (2023)](https://arxiv.org/abs/2210.03629)。

### 2.6 Long horizon、partial observability 与 off-policy 数据

Agent 任务通常是 POMDP：当前 prompt/history 未必包含完整环境状态，网页、搜索、用户和工具也可能变化。因此：

- 需要记录 observation、tool version、随机种子和完整 action trace，否则训练数据不可复现；
- context truncation 会破坏"当前 state 包含决定 credit 的原因"的假设；memory/retrieval policy 本身也应被视为 action；
- 基于旧 policy 的日志做离线更新会出现分布偏移：新 policy 会走到日志没有覆盖的状态；
- 仅在离线成功轨迹上做 SFT 不能解决失败恢复与探索；on-policy 或近 on-policy rollout 更贴近真实 Agent RL，但代价更高。

### 2.7 Reward 与 credit assignment 必须共同设计

二者不能独立选择：

| Reward 设计 | 更匹配的 credit 设计 | 原因 |
| --- | --- | --- |
| 终局、确定性 verifier | trajectory 或 turn advantage + value baseline | 真实目标强，但需降方差 |
| 可信的子目标/状态 verifier | step/tool-level reward | 中间状态能提供有意义的局部因果证据 |
| LLM judge 的模糊整体评分 | 先用 trajectory/turn，谨慎 densify | 将不可靠 judge 扩散到每一步会放大偏差 |
| 多 Agent 共享回报 | counterfactual / difference-style baseline | 需要分离协作者的边际贡献 |
| 强成本或安全约束 | action-level hard check + 局部 penalty | 违规必须立即阻断，不能等终局再归因 |

一个可操作的研究起点是：先搭建有**终局状态 verifier**的环境；把 turn-level 作为主训练单元；再仅对可确定验证的 tool action 添加 step-level 信号；最后通过消融验证过程 reward 是否真的提升了未见任务的终局成功率，而非只提高训练 reward。
