
# Agent RL & Self-Evolution

> 目标：从整体到细节理解 **Agent Reinforcement Learning（Agent RL）** 与 **Agent Self-Evolution（Agent 自进化）**。本文先建立地图，再列出值得顺藤摸瓜的代表工作。它不是论文大全；论文和方法更新很快，优先记录概念清晰、可复现或有原始论文/代码的工作。

## 0. 一句话地图

- **Agent RL**：把 Agent 放进一个需要多步行动的环境中，用任务结果或过程反馈优化策略。
- **Agent Self-Evolution**：Agent 不只改变“这一次怎么回答”，而是根据经验持续修改自己的某个组成部分，例如 prompt、memory、skill、tool、workflow/harness，甚至模型参数或架构。
- 二者关系：RL 是一种训练/优化机制；Self-Evolution 是一种更宽的系统变化范式。Self-Evolution 可以用 RL，也可以用搜索、进化、反思、代码修改、LLM judge 或人工反馈。

```text
Environment / User / Tools
          ↓ observation
Agent state = context + memory + skills + policy
          ↓ action（文本、工具调用、代码、浏览器操作）
Feedback = outcome / process / preference / verifier
          ↓
更新：policy（RL）或 prompt / memory / tool / harness / model（Self-Evolution）
```

## 1. 为什么 Agent RL 不等于普通 LLM RL？

传统 RLHF/DPO 通常可以近似为：给定一个 prompt，模型生成一次 response，再获得一个 reward。Agent RL 则更接近 **POMDP**：

$$
s_t \rightarrow a_t \rightarrow o_{t+1}, r_t \rightarrow s_{t+1}
$$

其中 action 可能是一次完整的模型 turn 或一次工具调用；环境反馈会改变下一轮上下文。困难主要来自：

| 维度 | 普通 LLM post-training | Agent RL |
| --- | --- | --- |
| 决策长度 | 单次 response | 多轮、长轨迹 |
| action | token/response | reasoning、tool call、代码、浏览器操作 |
| 环境 | 静态数据集或偏好数据 | 动态环境、工具、网页、游戏、软件 |
| reward | 偏好分数或结果分数 | 终局成功、过程质量、工具正确性、成本/安全 |
| 核心难题 | 对齐与生成质量 | 探索、长期信用分配、状态表示、工具与环境共适应 |

注意：并不是“用了工具”就自动成为 Agent RL。关键问题是：是否存在可重复交互的环境、跨步骤决策，以及反馈是否用于更新策略或选择更好的策略。

## 2. Agent RL 的研究方向

### 2.1 按训练对象分类

1. **Policy / model RL**：直接更新 LLM 参数；常见算法包括 PPO、GRPO、PPO-style actor-critic 等。
2. **Prompt / context policy optimization**：冻结模型，优化 system prompt、任务提示、few-shot 示例或上下文组织。
3. **Tool-use policy learning**：学习何时调用工具、选择哪个工具、如何填参数、如何处理错误和重试。
4. **Multi-agent RL**：多个 Agent 协作、竞争或通过 self-play 学习；需要考虑联合策略、通信和非平稳性。
5. **Environment / curriculum optimization**：不仅训练 Agent，也生成任务、调整难度、扩充工具或改变反馈器，让学习信号更有效。

### 2.2 按 reward 分类

- **Outcome reward**：任务最终是否完成，适合数学、代码执行、游戏胜负等可验证任务，但通常稀疏。
- **Process reward**：对每个 turn、步骤或工具调用评分，能改善 credit assignment，但容易被 reward hacking。
- **Programmatic verifier**：编译器、单元测试、浏览器状态、数据库状态等程序化验证器，通常比纯 LLM judge 更稳定。
- **Preference / LLM-as-judge**：适合开放域任务；需要校准 judge，防止风格偏好替代真实任务成功。
- **Composite reward**：成功率 + 工具正确性 + token/时间成本 + 安全约束，适合真实 Agent，但权重设计困难。

#### 2.2.1 先区分：reward 的来源、粒度与优化目标

一条 Agent 轨迹可写成 $\tau=(s_0,a_0,o_1,\ldots,s_T,a_T)$。奖励设计不是只选一个打分器，而是决定：

$$
R(\tau)=r_{\text{task}}+\lambda_p\sum_t r^{(p)}_t-\lambda_c C(\tau)-\lambda_s S(\tau)
$$

- $r_{\text{task}}$：最终任务是否达成；
- $r^{(p)}_t$：第 $t$ 步的过程信号；
- $C(\tau)$：成本，如 token、工具调用次数、延迟或金钱；
- $S(\tau)$：安全/约束违规的惩罚。

这里的公式是一个**设计模板**，不意味着实际系统必须线性加权。需要分别问清：奖励从哪里来、在何时给、能否被 agent 操纵、它是否真的与部署目标一致。

#### 2.2.2 五类主要 reward source

| 类型 | 信号从哪里来 | 优点 | 主要风险 | 典型 Agent 例子 |
| --- | --- | --- | --- | --- |
| **终局/结果奖励（ORM）** | 最终答案、任务状态、胜负 | 与最终目标直接对齐；定义简单 | 长任务中极稀疏，探索和 credit assignment 困难 | 网购是否买到目标商品、代码是否通过隐藏测试 |
| **过程奖励（PRM）** | 对中间 reasoning / turn / action 的打分 | 信号密、方差低、利于诊断 | judge 不准会把错误局部策略固化；可被“写得像正确步骤”欺骗 | 搜索查询是否相关、工具参数是否合理、子目标是否完成 |
| **程序化验证器** | 编译器、测试、状态机、数据库、浏览器 DOM | 可复现、可扩展，通常比语言 judge 稳定 | 只验证代理指标时会被钻空子；隐藏测试仍可能不足 | 单测通过率、SQL 执行结果、页面完成状态 |
| **偏好/LLM judge** | 人类比较、rubric、强模型评审 | 能覆盖开放式质量与多目标偏好 | position/length/style bias；judge 与被训模型同源时可能共谋 | 研究助理报告质量、客服回复帮助性 |
| **内在/探索奖励** | 新颖性、不确定性、信息增益、技能覆盖 | 稀疏任务中鼓励探索和发现 | 容易“为探索而探索”，与用户目标脱钩 | 未见 API、复杂游戏或开放世界中的状态覆盖 |

**结果奖励**适合结果可验证的环境。DeepSeekMath 与 DeepSeek-R1 表明，规则化正确性/格式奖励可以支撑 reasoning RL；但它们的核心任务仍不同于带外部状态和副作用的工具型 Agent。参考：[DeepSeekMath (2024)](https://arxiv.org/abs/2402.03300)、[DeepSeek-R1 (2025)](https://arxiv.org/abs/2501.12948)。

**过程奖励**的核心前提是“局部好”与“最终好”高度相关。[*Let's Verify Step by Step* (2023)](https://arxiv.org/abs/2305.20050) 显示了过程监督在数学推理上的价值；迁移到 Agent 时，评分对象不应只看自然语言 thought，还应覆盖可执行 action、环境 observation 与状态变化。

#### 2.2.3 程序化 verifier：最强信号也有边界

对于 Web、代码、数据库、游戏等环境，优先把**任务真实状态**编码为 verifier：

- 软件工程：补丁能否编译、测试是否通过、是否引入回归；
- Web：目标页面的 DOM/后端状态是否真的发生目标改变，而不是 agent 声称“已完成”；
- 数据库：返回值、写入状态、权限和事务约束；
- 工具调用：schema 合法性、参数类型、是否产生预期的状态转移。

这优于“LLM 读一下轨迹并给分”，但仍要防止 **proxy gaming**：若只奖励“测试通过”，Agent 可能修改测试；若只奖励“页面到达”，它可能绕过真实购买/提交语义。因此 verifier 需要：隐藏测试、不可由 Agent 修改的执行边界、对副作用的审计，以及与最终用户目标一致的状态谓词。可参考交互式环境设计：[WebShop (2022)](https://arxiv.org/abs/2207.01206)、[WebArena (2023)](https://arxiv.org/abs/2307.13854)。

#### 2.2.4 LLM judge 与 preference reward：什么时候不得不用？

开放任务（研究、写作、复杂客服）没有唯一正确状态，常需 judge 或人类偏好。推荐将 judge 设计成**可执行 rubric**，至少分开评估：任务完成度、事实性/引用、约束遵循、可执行性、风险与成本；避免一个“总体好不好”的模糊分数。

实践上应做四类校准：

1. **成对比较与顺序随机化**：减少 position bias；
2. **长度归一或简洁性约束**：减少 verbosity bias；
3. **与小规模人工标注对照**：报告 judge-human agreement，而非只报告 judge score；
4. **对抗样本**：故意构造语气自信但事实错误、格式完美但未执行工具的轨迹。

RLHF 的偏好建模框架可作为背景参照：[InstructGPT (2022)](https://arxiv.org/abs/2203.02155)。但在 Agent 场景中，judge 最好评判**环境证据 + 轨迹**，而不只是最终文本。

#### 2.2.5 Reward shaping 与 temporal densification

终局 $0/1$ reward 太稀疏时，可以加入中间信号，例如：

- 子目标完成：找到正确文档、获得有效 API token、定位可复现的 bug；
- action validity：工具名、参数、权限、调用顺序合法；
- progress：状态到目标状态的距离下降；
- efficiency：在成功前提下减少调用、token 和 wall-clock time；
- safety：越权、数据泄露、破坏性动作给大惩罚或直接终止。

但 shaping 的底线是：**它应帮助到达终局目标，而不能替代终局目标**。若只奖励“每一步都看似合理”，Agent 会学会冗长解释；若过度惩罚调用次数，Agent 会过早停止。较稳妥的顺序是：先建立可信终局 verifier，再增量加入少量、可消融的过程项；同时始终单独报告未加 shaping 的真实成功率。

#### 2.2.6 Composite reward 的常见陷阱与实验设计

多目标 reward 常写成加权和，但权重 $\lambda$ 实际上定义了产品取舍。建议：

- 将**硬安全约束**（不可越权、不可破坏生产数据）放在环境/动作层拦截，而非只给软 penalty；
- 将“成功率”和“成本”分别报告，避免一个总分掩盖 trade-off；
- 对每个 reward component 做消融，检查性能来自任务能力还是投机利用某个子项；
- 检查 train reward 与 holdout、人工评估、真实状态成功率的相关性；
- 保存完整 trajectory，人工审计高分失败与低分成功样本。

> 一个实用原则：**能由环境确定性验证的部分，不要交给 LLM judge；必须用 judge 的部分，不要让它单独决定任务成功。**

### 2.3 按 credit assignment 粒度分类

- **Token-level**：适合短 response，但对长轨迹不自然。
- **Turn-level**：一次模型 response 加环境反馈作为 macro-action；实现简单，是目前常见折中。
- **Step/tool-level**：把搜索、代码执行、API 调用等作为步骤，更容易定位错误。
- **Trajectory-level**：只在最终成功/失败时更新，信号最接近真实目标，但方差和探索难度最大。

#### 2.3.1 问题的精确定义

Credit assignment 问的是：得到最终回报 $R$ 后，**哪些过去的决策应得到多少正/负更新**。对第 $t$ 个决策，policy gradient 常通过 advantage 进行更新：

$$
\nabla_\theta J \approx \sum_t \nabla_\theta\log\pi_\theta(a_t\mid s_t)\,A_t,
\qquad
A_t=G_t-V(s_t)
$$

其中 $G_t$ 是从 $t$ 往后的 return，$V(s_t)$ 是 baseline。难点不在公式本身，而在 Agent 中：$a_t$ 可以是一段数百 token 的 response、一次工具调用或一个子计划；$s_t$ 只是部分可观测的上下文；终局 reward 可能在几十轮之后才出现。

#### 2.3.2 粒度并非“越细越好”

| 粒度 | action 单元 | 优点 | 代价/风险 | 更适合的场景 |
| --- | --- | --- | --- | --- |
| **Token** | 一个 token | 与自回归模型天然匹配；能微调语言形式 | 同一终局 reward 被复制到大量 token，噪声大且难解释工具因果 | 短答案、格式受控生成 |
| **Turn** | 一次完整 LLM response | 把 reasoning + tool call 视为 macro-action，训练接口较简单 | 一个 turn 内好坏混杂；长 turn 仍有归因误差 | 多轮 tool-use 的强基线 |
| **Step/tool** | 搜索、调用、代码执行、子目标 | 对应环境状态转移，可定位无效/危险 action | 需要定义 step 边界和局部 verifier；thought 与 action 的归因仍耦合 | API、浏览器、代码、数据库 Agent |
| **Trajectory** | 整条 episode | 与真实终局目标最一致，不要求局部标签 | 信号极稀疏、高方差、探索困难 | 高可信终局 verifier、短到中等 horizon |
| **层级（hierarchical）** | plan / option / low-level action | planner 管“做什么”，executor 管“怎么做”，可缩短有效 horizon | 需要可靠的子目标与 option 边界；错误 plan 会污染下层 | 长程任务、可分解工作流 |

以“修复一个 bug”为例：Agent 先搜索代码、再阅读文件、编辑补丁、跑测试、提交结果。若测试失败，trajectory-level 方法只能说“整条轨迹不好”；step-level verifier 可以指出“搜索结果不相关”“编辑未通过编译”还是“测试选择错误”。但若补丁最终通过所有隐藏测试，前面看似绕路的搜索也可能是必要探索——因此不能机械地把每个局部失败都当作负 reward。

#### 2.3.3 从稀疏终局 reward 到中间 credit 的四条路线

1. **学习 value / advantage baseline**：用 $V(s_t)$ 预测从当前状态成功的概率或未来 return，再用 $G_t-V(s_t)$ 降低方差。GAE 是经典 bias–variance 折中工具：[Generalized Advantage Estimation (2015)](https://arxiv.org/abs/1506.02438)。
2. **过程 reward model（PRM）或局部 verifier**：为 turn/step 产生中间 reward，直接 densify 信号。风险是 PRM 的偏差会系统性改变优化目标。
3. **Reward redistribution**：将终局 reward 根据“何时出现了决定性信息”重新分配到较早步骤，而不只是平均摊给所有 token；此思路的 RL 原型见 [RUDDER (2019)](https://arxiv.org/abs/1806.07857)。
4. **反事实/差分 credit**：比较“有该 action”和“替换/移除该 action”后的 outcome，近似其边际贡献。多 Agent 的 COMA 用 counterfactual baseline 分离各 Agent 对共享回报的贡献：[COMA (2017)](https://arxiv.org/abs/1705.08926)。单 Agent tool-use 中也可用 replay、action ablation 或 simulator 做近似，但成本通常很高。

#### 2.3.4 Turn-level 为什么是常见折中？

一个 Agent turn 往往同时输出 reasoning、决定是否调用工具、填参数，并得到 observation。把这个闭环作为 macro-action 有三点好处：

1. 环境只需在 turn 边界 reset/record，工程实现和并行 rollout 更可控；
2. 工具 observation 能进入下一状态，符合实际交互语义；
3. 相比 token-level，reward 不会在长文本中被无意义地重复广播。

它的代价是：模型可能在同一 turn 中产生很长的错误推理后又给出正确 tool call，或反之；同一个 advantage 更新会同时强化两者。可用更短 turn、结构化 action（thought / tool / final 分段）或在关键 action 上加 verifier 来缓解。

#### 2.3.5 Step/tool-level：最适合真实工具环境的接口

建议把可执行 action 显式结构化，例如：

```text
state: 目标 + 已观察到的页面/代码/数据库状态
action: {tool_name, arguments}
observation: 工具返回 + 可信状态摘要
local checks: schema valid? permission valid? state changed as expected?
```

这样可以对“调用无效 API”“参数类型错误”“重试同一失败调用”“写入了错误表”等事件给出局部 credit。但不要把自然语言 thought 当作可靠的因果解释：真正应优先归因的是**环境可观察的 action 和状态转移**。ReAct 将 reasoning 与 acting 交替呈现，是理解这一接口的有用起点：[ReAct (2023)](https://arxiv.org/abs/2210.03629)。

#### 2.3.6 Long horizon、partial observability 与 off-policy 数据

Agent 任务通常是 POMDP：当前 prompt/history 未必包含完整环境状态，网页、搜索、用户和工具也可能变化。因此：

- 需要记录 observation、tool version、随机种子和完整 action trace，否则训练数据不可复现；
- context truncation 会破坏“当前 state 包含决定 credit 的原因”的假设；memory/retrieval policy 本身也应被视为 action；
- 基于旧 policy 的日志做离线更新会出现分布偏移：新 policy 会走到日志没有覆盖的状态；
- 仅在离线成功轨迹上做 SFT 不能解决失败恢复与探索；on-policy 或近 on-policy rollout 更贴近真实 Agent RL，但代价更高。

#### 2.3.7 Reward 与 credit assignment 必须共同设计

二者不能独立选择：

| Reward 设计 | 更匹配的 credit 设计 | 原因 |
| --- | --- | --- |
| 终局、确定性 verifier | trajectory 或 turn advantage + value baseline | 真实目标强，但需降方差 |
| 可信的子目标/状态 verifier | step/tool-level reward | 中间状态能提供有意义的局部因果证据 |
| LLM judge 的模糊整体评分 | 先用 trajectory/turn，谨慎 densify | 将不可靠 judge 扩散到每一步会放大偏差 |
| 多 Agent 共享回报 | counterfactual / difference-style baseline | 需要分离协作者的边际贡献 |
| 强成本或安全约束 | action-level hard check + 局部 penalty | 违规必须立即阻断，不能等终局再归因 |

一个可操作的研究起点是：先搭建有**终局状态 verifier**的环境；把 turn-level 作为主训练单元；再仅对可确定验证的 tool action 添加 step-level 信号；最后通过消融验证过程 reward 是否真的提升了未见任务的终局成功率，而非只提高训练 reward。

### 2.4 Agent RL 的工程瓶颈

1. **长轨迹训练成本**：一次 rollout 可能包含很多 LLM turn 和昂贵工具调用。
2. **环境吞吐**：训练需要大量并行、可重置、可记录的环境。
3. **信用分配**：最后成功往往由多个决策共同造成，很难判断哪一步值得奖励。
4. **探索与安全**：真实工具中的错误探索可能产生副作用。
5. **reward hacking / specification gaming**：Agent 学会钻验证器空子，而不是完成真实目标。
6. **评测污染**：训练环境、工具文档和 benchmark 泄漏会夸大效果；应报告未见任务、成本、失败类型和轨迹。

| **AgentBench: Evaluating LLMs as Agents** | 2023 | 多环境 Agent benchmark；重点看评测维度而非把 benchmark 当训练算法 | [paper](https://arxiv.org/abs/2308.03688) |
| **WebShop: Towards Scalable Real-World Web Interaction with Grounded Language Agents** | 2022 | 网页环境、动作空间、成功率和交互式决策 | [paper](https://arxiv.org/abs/2207.01206) |
| **ALFWorld: Aligning Text and Embodied Environments for Interactive Learning** | 2021 | 文本环境与 embodied 环境对齐；适合研究长程规划和稀疏反馈 | [paper](https://arxiv.org/abs/2010.03768) |
| **RAGEN: Training Agents through Reinforcement Learning** | 2025 | 长轨迹 Agent RL 的训练不稳定、探索与 credit assignment；阅读时核对其具体算法定义 | [paper search](https://arxiv.org/search/?query=RAGEN+Training+Agents+through+Reinforcement+Learning&searchtype=all) |
| **ToRL: Scaling Tool-Integrated Reinforcement Learning for LLMs** | 2025 | 把工具调用纳入 RL rollout；关注工具环境与训练循环如何耦合 | [paper search](https://arxiv.org/search/?query=ToRL+Scaling+Tool-Integrated+Reinforcement+Learning&searchtype=all) |
| **DeepSeek-R1: Incentivizing Reasoning Capability in LLMs via Reinforcement Learning** | 2025 | GRPO、可验证 reward 和长 chain-of-thought RL；并非完整 Agent RL，但提供重要训练基线 | [paper](https://arxiv.org/abs/2501.12948) |

> 阅读提示：DeepSeek-R1 是 reasoning RL 的关键参照，不应直接等同于 tool-using Agent RL；Agent RL 的新增变量是环境状态、工具副作用和跨 turn credit assignment。

## 4. Agent Self-Evolution 是什么？

### 4.1 判定标准

一个系统只有在“经验导致了持久的自我修改”时，才适合称为 self-evolution。至少要回答四个问题：

1. **改什么（object）**：prompt、memory、skill、tool、harness、policy、model 或 architecture？
2. **谁来改（optimizer）**：RL、进化搜索、LLM critic、代码生成器、梯度更新还是人工？
3. **依据什么改（feedback）**：成功率、verifier、用户偏好、轨迹反思、成本或安全指标？
4. **是否持久化（persistence）**：改动是否影响后续独立任务？

固定的 ReAct 循环、每次都重新 self-critique、或者只在当前上下文中重写答案，通常是 inference-time reasoning，而不是严格意义上的 self-evolution。

### 4.2 六个主要方向

| 方向 | 被进化的对象 | 常见反馈/优化器 | 典型产物 |
| --- | --- | --- | --- |
| **Prompt evolution** | system prompt、instruction、few-shot、meta-prompt | evolutionary search、LLM critic、黑盒优化 | 新 prompt、规则集 |
| **Memory evolution** | episodic/semantic memory、摘要、检索索引 | 成功/失败轨迹、反思、memory manager | 可复用经验、策略摘要 |
| **Skill / tool evolution** | skill library、tool schema、工具实现、调用策略 | 任务成功率、执行器、代码生成 | 新工具、技能卡、调用 policy |
| **Harness / workflow evolution** | planner、router、验证器、重试逻辑、multi-agent topology | benchmark score、trajectory judge、搜索 | 新工作流、代码化 agent scaffold |
| **Policy / model evolution** | 权重、adapter、policy、子模块或架构 | RL、SFT、self-play、梯度/进化搜索 | 新 checkpoint 或 agent architecture |
| **Data / feedback evolution** | 训练任务、curriculum、合成数据、reward/verifier | active learning、自动出题、self-play | 更难任务、更好数据和反馈器 |

这些方向不是互斥的：例如，一个系统可能从失败轨迹中提炼 memory，再由 memory 改 prompt，最后用 RL 更新 policy。

## 5. Self-Evolution 各方向的代表工作

### 5.1 Prompt evolution

- **Promptbreeder: Self-Referential Self-Improvement via Prompt Evolution**（2024）：让 prompt 和“生成/变异 prompt 的 mutation prompt”共同进化，代表 self-referential prompt evolution。[ICML 页面](https://proceedings.mlr.press/v235/fernando24a.html)
- **ProTeGi: Gradient-free Prompt Optimization through Iterative Editing**（2023）：用自然语言“梯度”指导 prompt 编辑，是 prompt 优化和 self-evolution 的重要黑盒基线。[paper](https://arxiv.org/abs/2305.03495)
- **DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines**（2024）：把 prompt、示例和模块编译/优化为可评测 pipeline；更准确地说是可编程优化框架，不等同于完全自主 self-evolution。[project](https://github.com/stanfordnlp/dspy)

本地可交叉阅读：[[2. Agent Prompt Auto Opt]]、[[3. Adaptive prompt for diff LLM]]。

### 5.2 Memory evolution

- **Reflexion: Language Agents with Verbal Reinforcement Learning**（2023）：把语言形式的反思写入 memory，供后续试验使用；是“非参数化 verbal RL”的经典入口。[paper](https://arxiv.org/abs/2303.11366)
- **ExpeL: LLM Agents Are Experiential Learners**（2023）：从成功/失败轨迹抽取可迁移经验，用于后续任务决策。[paper search](https://arxiv.org/search/?query=ExpeL+LLM+Agents+Are+Experiential+Learners&searchtype=all)
- **Voyager: An Open-Ended Embodied Agent with Large Language Models**（2023）：通过自动课程、技能库和迭代反馈实现 Minecraft 中的 lifelong skill accumulation；同时涉及 skill evolution。[paper](https://arxiv.org/abs/2305.16291)

关键问题：memory 不是越多越好。研究重点包括写入门控、摘要粒度、经验去重、时间衰减、检索相关性、错误记忆修正和跨任务迁移。

### 5.3 Skill / tool evolution

- **Voyager**：将可执行代码技能写入 skill library，并根据环境反馈迭代修复，是 skill accumulation 的代表。[project](https://voyager.minedojo.org/)
- **Toolformer: Language Models Can Teach Themselves to Use Tools**（2023）：通过自监督数据让模型学习何时调用 API；更偏 tool-use learning，但为后续 tool policy evolution 提供基础。[paper](https://arxiv.org/abs/2302.04761)
- **TOOLMAKER: Task-Oriented Tool Use for LLM Agents**（2024）：研究从已有资源构建/使用工具的 Agent 范式；阅读时区分“生成工具”与“只选择预定义工具”。[paper search](https://arxiv.org/search/?query=TOOLMAKER+LLM+agents&searchtype=all)

### 5.4 Harness / workflow evolution

- **Automated Design of Agentic Systems (ADAS)**（2024）：用搜索自动发现 Agentic system 的组合式设计，直接触及 planner、critic、工具和模块连接方式的演化。[paper search](https://arxiv.org/search/?query=Automated+Design+of+Agentic+Systems+ADAS&searchtype=all)
- **DSPy**：把模块、签名、示例和优化器组合成可编译 pipeline；适合作为“harness 可优化但未必自主在线进化”的边界案例。[project](https://github.com/stanfordnlp/dspy)
- **SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering**（2024）：其核心贡献是为软件工程 Agent 设计有效的 agent-computer interface；本身不是 self-evolution，但说明 harness/interface 设计会显著改变 Agent 能力。[paper](https://arxiv.org/abs/2405.15793)

Harness evolution 的研究对象不是某一条 prompt，而是整个控制程序：何时规划、何时检索、如何分解、如何并行、何时验证、失败后如何重试，以及多个 Agent 如何通信。

### 5.5 Policy / model / architecture evolution

- **Self-Refine: Iterative Refinement with Self-Feedback**（2023）：利用生成-反馈-修改循环提升单次任务结果；可视为 inference-time self-improvement 的基线，但没有参数更新。[paper](https://arxiv.org/abs/2303.17651)
- **SPIN: Self-Play Fine-Tuning Converts Weak Language Models to Strong Language Models**（2024）：通过 self-play 构造数据并进行参数更新，代表 model-level self-improvement。[paper](https://arxiv.org/abs/2401.01350)
- **SEAL: Self-Adapting Language Models**（2025）：研究模型根据经验生成自适应更新信号/数据，从而改变自身能力；应重点关注其更新边界和评测设置。[paper search](https://arxiv.org/search/?query=SEAL+Self-Adapting+Language+Models&searchtype=all)
- **Darwin Gödel Machine**（2025）：探索能修改自身代码、运行实验并保留改进版本的 Agent 系统；是代码/架构层 self-evolution 的代表性方向。[paper search](https://arxiv.org/search/?query=Darwin+Godel+Machine&searchtype=all)

### 5.6 Data / feedback evolution

- **Self-Refine**：通过自反馈生成新的训练/决策信号，但默认不做参数更新，适合用来区分“feedback loop”和“learning loop”。
- **STaR: Bootstrapping Reasoning With Reasoning**（2022）：用模型自身生成的正确 reasoning 逐步构造训练数据，代表“从成功轨迹反哺数据”的范式。[paper](https://arxiv.org/abs/2203.14465)
- **AlphaEvolve: A Gemini-powered coding agent for designing advanced algorithms**（2025）：用自动评测驱动程序/算法的进化搜索；不是通用 Agent RL，但展示了 verifier、候选程序和进化循环如何组成强反馈系统。[blog](https://deepmind.google/discover/blog/alph​​aevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)

## 6. Agent RL 与 Self-Evolution 的统一视角

可以把系统写成一个双层优化问题：

$$
\text{inner loop: } \tau \sim \pi_\theta(\cdot\mid s), \quad R(\tau) \\
\text{outer loop: } z_{k+1}=\Phi(z_k, \tau, R), \quad z\in\{prompt,memory,tool,harness,\theta\}
$$

- Agent RL 通常关注：给定 agent 结构，如何学习 $\pi_\theta$。
- Self-Evolution 关注：如何选择和修改 $z$，而 $z$ 可以包含 policy 之外的系统组件。
- 最有潜力的组合是 **experience → memory/skill → better rollout → verifier/reward → policy/harness update**，也就是一个可测量的 evolution flywheel。

## 7. 建议的学习顺序

1. **Agent 基础**：ReAct、Toolformer、AgentBench、WebShop、ALFWorld。
2. **经验与 memory**：Reflexion、ExpeL、Voyager；理解 verbal feedback、skill library 和跨任务迁移。
3. **Prompt / pipeline optimization**：本目录的 [[2. Agent Prompt Auto Opt]]、Promptbreeder、ProTeGi、DSPy。
4. **Reasoning RL**：PPO/GRPO、DeepSeek-R1；再进入多轮 Agent RL，避免把单轮 reasoning RL 和 Agent RL 混在一起。
5. **Agent RL 系统**：AgentGym、工具环境、可验证 reward、trajectory/turn/step-level credit assignment。
6. **Harness / architecture evolution**：ADAS、Darwin Gödel Machine，以及 Agent 自己修改代码/工具/工作流时的安全和评测问题。

## 8. 研究问题清单

- 如何定义跨任务、跨环境的“真正进步”，而不是对单一 benchmark 过拟合？
- memory、prompt、tool、harness 和 model 同时变化时，如何做因果归因？
- 长轨迹中的最优 credit assignment 粒度是 turn、step、tool 还是层级混合？
- LLM judge、程序 verifier 和用户反馈如何组合，才能减少 reward hacking？
- Agent 修改自己的工具或代码时，如何进行沙箱、安全审计、回滚和版本选择？
- Self-Evolution 是否会导致 capability gain 与 reliability、可解释性、成本之间的 trade-off？
- 评测是否应从单次成功率扩展为：学习曲线、跨任务迁移、持续性、灾难性遗忘、成本和安全？
