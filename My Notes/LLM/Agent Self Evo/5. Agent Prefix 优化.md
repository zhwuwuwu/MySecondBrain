# Agent Prefix 优化：长 System Prompt 的推理加速（Prefix Cache / Infra 层）

> 范围：区别于 [[3. Adaptive prompt for diff LLM]] 系列笔记关心的"跨模型行为一致性"，这里关心纯粹的**推理速度**问题——当 agent 的 system prompt 长达数千到数万 token 时，prefill（首 token 前的预填充计算）会成为明显的延迟瓶颈，如何在 prompt 层级和 infra 层级把这部分成本降下来。
> 核心思路只有两条，且完全正交、可叠加：**(1) 复用**——同一段 prefix 算过一次就别再算第二次（prefix caching）；**(2) 变短**——从根源减少要 prefill 的 token 数（prompt 压缩、投机式 prefill）。工程实践上两者叠加使用。

---

## 0. 问题定义

Transformer 推理分两阶段：**prefill**（一次性处理全部输入 prompt，计算量随 prompt 长度 $n$ 近似线性增长，是 compute-bound）和 **decode**（逐 token 生成，是 memory-bandwidth-bound）。Agent 场景的典型模式是：**一段几千到几万 token 的、几乎不变的 system prompt（角色+工具定义+工作流规则） + 每轮很短的动态用户输入/工具返回**。这个模式下，如果每一轮都把整段 system prompt 重新 prefill 一次，绝大部分计算都在做重复劳动——这正是本笔记要解决的问题。

---

## 1. Prefix Caching：复用已经算过的 KV Cache

### 1.1 核心机制

存储已处理 token 的 KV cache，任何未来请求只要 token 前缀匹配，就直接复用缓存，跳过对应部分的 prefill 计算。

**生产级实现**：
- **SGLang RadixAttention**：用 radix tree（前缀树）管理 KV cache，支持任意子串级别的复用，不局限于精确的"完整 prefix"匹配。
- **vLLM Automatic Prefix Caching（APC）**：基于 hash block 的实现，按 block 粒度做前缀复用。

**效果量级**：100% 命中系统提示词缓存的 agent 循环场景下，TTFT（首 token时间）可降低 **70–80%**；吞吐量（output tok/s）提升 **2–3 倍**；4K–48K token 的前缀命中延迟可以做到 **4–8 毫秒**，相比冷 prefill 的数百毫秒是量级差异。

**核心洞察**：对 agent 而言，"几千 token 的 system prompt + 工具定义在每个请求里重复出现"正是这个技术的典型工作负载——用了 prefix caching 之后，system prompt 的计算成本变成"每个缓存驱逐窗口（通常几分钟）付一次"，而不是"每个请求都付一次"。

### 1.2 复用不是免费的——缓存驱逐与命中率

前缀缓存不是无限容量，会有 LRU 或更智能的驱逐策略。多 agent / 多用户共享同一模型时，如果不同 agent 的前缀差异很大，缓存命中率会下降。这催生了更精细的"workflow-aware KV 管理"这一类后续工作（见第 3.4 节）。

## 2. 三大 Provider 的 Prompt Caching API 对比

三家目前都支持 prefix/prompt caching，机制、计价、结构化建议略有不同，但核心原则完全一致：**静态内容放前面，动态内容放后面**。

| 维度 | Anthropic Claude | OpenAI | Google Gemini |
|---|---|---|---|
| 机制 | 显式 `cache_control` 断点（最多 4 个/请求），或单个顶层字段自动滑动断点 | 默认自动缓存（早期模型，同机路由后精确前缀匹配）；GPT-5.6+ 支持显式断点（Responses API `compact` / `prompt_cache_key`） | 隐式缓存（Gemini 2.5+ 默认开启，无需开发者操作）+ 显式缓存（`client.caches.create`，适合文件类大内容） |
| 最小可缓存前缀 | 模型相关：Opus 5 为 512 token（从 1024 下调），其余模型 1024–4096 token | 1024 token（早期模型 1024–2048，视模型而定） | 2048 token（2.5 系列）/ 4096 token（3.1+ 系列） |
| Cache TTL | 5 分钟（默认，写入费 1.25×）或 1 小时（写入费 2×），按断点可选 | 自动缓存无显式 TTL（best-effort，不常用即被驱逐）；显式断点默认 30 分钟，可配置到 24 小时 | 隐式：短时间窗口内自动生效；显式：开发者自定义，历史上限约 1 小时 |
| 命中价格折扣 | **读命中 0.1×**（90% 折扣） | **读命中 0.1×**（90% 折扣） | 约 **75% 折扣**（如 Gemini 2.5 Pro 缓存价 $0.125 vs 原价 $1.25/1M token） |
| 官方结构化建议 | "把工具定义、系统指令等静态内容放在 prompt 最前面"，处理顺序固定为 tools → system → messages | "把指令、schema、示例、工具放最前面，用户输入放最后";多轮对话只追加不重写 | "把大块共享内容放最前面，短时间内发送前缀相似的请求以提高隐式命中率" |
| 延迟数字 | 2024 发布时宣称"最高降低 80% 延迟、90% 成本"（未按 Opus 5 更新过具体数字） | 未公布具体百分比；官方原话："输入 token 减半通常只带来 1-5% 的延迟提升，prompt caching 的主要收益来自 agent 场景里的共享前缀，而不是逐 token 加速" | 未公布具体百分比 |

### 2.1 三家共同的设计原则

1. **静态内容在前，动态内容在后**——三家文档都逐字写了这条规则。
2. **只追加、不重写历史**——OpenAI 明确写"不要重写/删除/重排早期消息"；Anthropic 的滑动断点模型隐含同样约束；Gemini 的 `previous_interaction_id` 机制效果一致。
3. **缓存前缀长度门槛随模型不同**，短 prompt 可能根本触发不了缓存（低于门槛时正常处理、不报错，但也不省钱）。

### 2.2 给长 Agent System Prompt 的具体排布建议

综合三家指南，推荐的从上到下排布顺序：

1. **工具定义**（最少变化，往往也是最大的一块，放最前面单独设一个缓存断点）
2. **静态系统指令**（人设、规则、输出格式）
3. **长期参考材料**（RAG 内容、知识库，如果有）
4. **只追加的多轮对话历史**
5. **当前用户输入 + 工具返回结果**（永远放最后，不能出现在任何缓存断点之前）

其他工程要点：
- **预热（pre-warming）**：Anthropic 建议启动时发一个 `max_tokens=0` 的哨兵请求把 system prompt 的 KV 提前计算好；OpenAI 靠稳定的 `prompt_cache_key` 做路由；Gemini 用显式缓存在启动时创建。
- **按流量模式选 TTL**：慢节奏的后台 agent 用 1 小时/24 小时长 TTL；交互式场景用默认的 5/30 分钟。
- **监控缓存写入异常**：如果观察到"反复写入却没有复用"，通常意味着动态内容被错误地放在了缓存断点之前。

## 3. Serving 层的进阶技术（超越简单前缀缓存）

前缀缓存解决的是"重复内容"问题，下面这些技术解决的是"新内容/未命中部分怎么算得更快"的问题，全部可以和前缀缓存叠加使用。

### 3.1 Chunked Prefill（Sarathi-Serve）

**论文**：Agrawal et al., *Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve*，OSDI 2024（[arXiv 2403.02310](https://arxiv.org/abs/2403.02310)，[代码](https://github.com/microsoft/sarathi-serve)）

**核心思想**：把一次长 prefill 切成很多计算量均匀的小 chunk（如 512–2048 token），每个 chunk 和正在进行的 decode 迭代拼成一个无停顿的混合 batch，用固定 token 预算控制每次迭代的计算量。

**解决的问题**：传统"先 prefill 再 decode"调度下，一次长 prefill 会阻塞 batch 里所有 decode 请求数百毫秒到数秒，naive 混合批处理会让 TBT（token 间延迟）飙升到 decode-only 的 **28.3 倍**。

**实测收益**：Mistral-7B/1×A100 服务容量 **+2.6×**；Yi-34B/2×A100 **+3.7×**；Falcon-180B/8×A100 **+5.6×**；LLaMA2-70B/8×A40 相比 Orca **+6.3×**、相比 vLLM **+4.3×**。

**对 agent 场景的意义（高相关）**：一个 20K token 的 system prompt 被切成 10-40 个 chunk，每个 chunk 和短的用户轮次 prefill、以及正在进行的 decode 一起跑，TTFT 随长前缀长度近似线性增长但 TBT 保持有界。**目前已是 vLLM v1 的默认调度模式**。

### 3.2 Prefill/Decode 分离部署（Disaggregated Serving）

Prefill 是 compute-bound（适合最新 GPU 如 H100），decode 是显存带宽-bound（旧/便宜 GPU 也能接受）——把两者放在同一台机器上会耦合两者的并行策略选择，造成互相干扰。分离部署把两阶段拆到不同硬件池，用高速互联（InfiniBand/RDMA）传输 KV cache。

| 系统 | 论文 | 核心机制 | 实测收益 |
|---|---|---|---|
| **Splitwise** | Patel et al., ISCA 2024（[arXiv 2311.18677](https://arxiv.org/abs/2311.18677)） | prompt 机器与 token 机器分池，KV cache 通过 MSCCL++ 异步传输 | 同成本 **+1.4× 吞吐/降 20% 成本**，或同预算 **+2.35× 吞吐** |
| **DistServe** | Zhong et al., OSDI 2024（[arXiv 2401.09670](https://arxiv.org/abs/2401.09670)，[代码](https://github.com/LLMServe/DistServe)） | 两阶段独立做并行策略+网络placement 联合优化，按 TTFT/TPOT SLO 反推资源配置 | **7.4× 更多请求**或**12.6× 更紧的 SLO**，同时保持 >90% 请求在延迟预算内 |
| **Mooncake**（Moonshot Kimi 生产系统） | Qin et al., FAST 2025（[项目页](https://kvcache-ai.github.io/Mooncake/)） | KVCache-centric：全局调度器 Conductor + 分布式 KV 池（CPU/DRAM/SSD/RDMA）+ chunked pipeline parallelism（长 prefill 跨多节点分块流水线） | 模拟长上下文负载 **+525% 吞吐**；生产环境 **+75% 请求量**（A800 集群 +115%，H800 +107%） |
| **TetriInfer** | Hu et al.（[arXiv 2401.11181](https://arxiv.org/abs/2401.11181)） | 固定块大小 chunked prefill + 分离部署 + LLM 长度预测器预调度 decode 资源 | **省 38% 硬件**、**TTFT -97%**、**JCT -47%**（轻 prefill 重 decode 混合负载） |

**对 agent 场景的意义**：多个 agent 共享同一段长 system prompt，一次性传输 KV 到 decode 池后即可复用；decode 侧可以用更便宜的硬件（agent 单轮输出通常不长）。Mooncake 的 chunked pipeline parallelism 尤其贴合"50K token 共享 system prompt + 短用户后缀"这个模式。已集成进 vLLM（`MooncakeConnector`/`NIXLConnector`）与 SGLang（PD-disagg via Mooncake Transfer Engine）。

### 3.3 投机式 Prefill（Speculative Prefill）

**论文**：Liu et al., *Speculative Prefill: Turbocharging TTFT with Lightweight and Training-Free Token Importance Estimation*，ICML 2025（[PMLR](https://proceedings.mlr.press/v267/liu25g.html)）

**核心思想**：用一个轻量草稿模型通过 attention 模式给 prompt 里每个 token 打"重要性分"，只把 top-k% 最重要的 chunk 送进目标模型做真正的 prefill（保留原始 position id，RoPE 位置关系不受影响）。跨模型家族的变体（[arXiv 2603.02631](https://arxiv.org/abs/2603.02631)）支持草稿/目标模型来自不同家族（Qwen↔LLaMA↔DeepSeek）。

**实测收益**：128K prompt 压到 16K，TTFT 46s→**2.5s（~18×）**；vLLM 在 Apple Silicon 上实现：64K token 417.6s→92.8s（**4.5×**），128K 19.3min→3.5min（**5.45×**）；端到端 QPS 最高 **+7×**（Llama-3.1-405B-Instruct-FP8）。

**⚠️ 重要限制——这是有损压缩**：与前缀缓存/chunked prefill 不同，投机式 prefill 会真正丢弃 token，是**有损**的。对 agent system prompt 而言，如果结构是"指令+工具+few-shot"，大部分 token 本身就是重要的，投机式 prefill 更适合用在**动态部分**（长 RAG 文档、增长的对话历史）而不是静态的 system prompt 本身——那部分应该老老实实交给前缀缓存处理。

### 3.4 Workflow-aware KV 管理（面向多 Agent 场景的下一层优化）

超越"精确前缀匹配"，预测接下来会用到哪些 KV cache 并提前 warm：

| 系统 | 机制 | 实测收益 |
|---|---|---|
| **Prompt Cache**（[arXiv 2311.04934](https://www.alphaxiv.org/abs/2311.04934)） | 预计算命名"prompt 模块"（系统指令、工具 schema）的 KV，在任意位置复用 | GPU **8× TTFT**，CPU **60× TTFT**（文档问答场景） |
| **KVFlow**（NeurIPS 2025） | 用"Agent Step Graph"预测下一步需要哪个 agent 的 KV，后台预取 | 单工作流 **1.83×**、多工作流 **2.19×**（相比 SGLang） |
| **CacheScout**（[arXiv 2608.14624](https://arxiv.org/html/2608.14624)） | 在线学习的 Markov 链建模 agent 调度顺序 | 命中率 **+10-18pp**，TTFT **-18~45%**，单轮延迟 **-29~38%**，吞吐 **+57%** |
| **CacheSlide**（FAST 2026） | "相对位置无关缓存"，处理固定段+动态段混合的 agent prompt | 延迟 **3.11-4.3×**、吞吐 **3.5-5.8×** |
| **ContextPilot**（MLSys 2026） | 超越精确前缀匹配：对齐+去重+顺序标注实现跨前缀复用 | prefill 延迟最高 **3×** 降低 |
| **TokenPilot**（[arXiv 2606.17016](https://arxiv.org/html/2606.17016v1)） | 显式协调"上下文精简"与"前缀缓存连续性"两个目标 | 长程 agent 持续模式下成本 **-56~87%** |

## 4. Prompt 压缩：从根源减少 Token 数——但对工具调用类 prompt 要谨慎

### 4.1 LLMLingua 系列

| 方法 | 机制 | 压缩比 | 备注 |
|---|---|---|---|
| **LLMLingua**（EMNLP 2023，[arXiv 2310.05736](https://arxiv.org/abs/2310.05736)） | 用小模型（GPT-2/LLaMA-7B）算每个 demo/token 的困惑度（perplexity），低困惑度的先丢；分 instruction/demonstration/question 三段分别设压缩预算 | 最高 **20×**（GSM8K，准确率仅降 1.5pt） | 逐 token 迭代打分，速度慢；48K token 时压缩本身耗时可达 13-21 秒 |
| **LLMLingua-2**（ACL 2024 Findings，[arXiv 2403.12968](https://arxiv.org/abs/2403.12968)） | 重新建模为**二分类任务**：用 XLM-RoBERTa 编码器预测每个词"保留/丢弃"，训练数据由 GPT-4 在 MeetingBank 上蒸馏得到 | **2-5×**，任务无关 | 比 v1 快 **3-7×**，压缩比更可控，是目前"唯一可用于生产"的版本（下面详述） |
| **LongLLMLingua**（MSR 项目页） | 查询感知：困惑度按问题条件化 + 按相关性重排文档 + 动态压缩率 | **4×** | RAG 场景 **+17.1%** 性能（用 1/4 token） |

### 4.2 关键陷阱：LLMLingua v1 的压缩开销可能超过它省下的时间

独立系统性研究（[arXiv 2604.02985](https://arxiv.org/abs/2604.02985)）实测：LLMLingua v1 在 48,000 token、1.5× 压缩率下，算法本身（非模型推理）开销高达 **13 秒**，总延迟 **21 秒**——因为算法是完全顺序执行的。**LLMLingua-2 把这部分开销压到 3 秒以内**，模型推理耗时稳定在 0.01-0.03 秒。该研究结论："只有 LLMLingua-2 在这些条件下是实用的"，且"只有在极长 prompt（>10,000 token）叠加 >4× 压缩率时才能观察到 >1.3× 的端到端加速"。

### 4.3 ⚠️ 对 Agent Tool-Calling System Prompt 的明确警告——这是本次调研最重要的工程提醒

**LLMLingua 系列训练/评测数据全部是 GSM8K、BBH、MeetingBank、LongBench 等数学推理/摘要/长文档问答任务，没有任何工具调用/function-calling 基准。** 工具 schema 结构上类似一段长指令，而官方文档自己的 `force_tokens`、`compress=False` 分段控制，本质上就是在说"别压缩真正重要的部分"。

生产环境报告（CallSphere，2026）明确写道：
> "用在文档问答和长上下文场景没问题；**千万别用在 tool-calling system prompt 上，那里每个 token 都在影响路由决策**。"
> "压缩会影响工具调用准确率吗？——**会。工具描述本身信息密度很高，压缩后参数准确率会掉 5-10 个点，建议跳过**。"

### 4.4 实用建议：压缩 + 缓存组合策略

1. **RAG 检索内容、较早的对话轮次**：可以大胆压缩（4-20×）。
2. **工具目录、系统指令、当前轮消息**：保持不压缩或极轻压缩（≤2×）。
3. **把整段前缀（系统提示+工具+压缩后的 RAG）一起做前缀缓存**——"压缩率" × "缓存命中率"是乘性收益：缓存住一段已经被压缩过 90% 的内容，等于在已经打了 9 折的基础上再打 9 折。

## 5. 落地清单：给"一个很长的共享 system prompt + 短动态用户轮次"这个模式的推荐组合

1. **前缀缓存打底**（APC/RadixAttention）——system prompt 在所有用户、所有轮次间保持热态，这是收益最大、实现成本最低的一步，没有理由不用。
2. **Chunked Prefill 兜底未命中部分**（Sarathi-Serve，vLLM 已默认开启）——防止任何没被缓存的前缀（新会话、RAG 内容、增长超出缓存窗口的历史）单次阻塞其他请求的 decode。
3. **流量上规模后引入 Prefill/Decode 分离**（Mooncake/DistServe/Splitwise）——把长 prefill 的算力预算和廉价 decode 的预算分开配置和扩缩容。
4. **对动态部分（不是静态 system prompt）考虑投机式 prefill**——长 RAG 文档、持续增长的对话历史里低重要性 token 可以丢，但静态 system prompt 本身不要动。
5. **Prompt 压缩仅用于 RAG/历史轮次，工具定义和系统指令原样保留**——第 4.3 节的警告不是理论担忧，是有具体数字的生产教训（参数准确率 -5~10pt）。
6. **多 agent/多工作流场景再上 workflow-aware KV 管理**（KVFlow/CacheScout/ContextPilot 等）——当"下一个请求会命中哪段缓存"本身可预测时，提前预取比被动 LRU 更有效。
