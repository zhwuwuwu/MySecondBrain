> **结论先行**：多模态 API 的价格差异不是简单的“图像/视频 token 更贵”，而是不同模态背后的成本单位不同。图像/音频/视频理解通常仍会先被编码成模型 token，因此可以沿用输入 token、输出 token、缓存 token 的计费体系；图像/视频/音频生成则往往是专门的生成模型或扩散/流匹配系统，算力与输出时长、分辨率、帧数、采样步数强相关，所以更常按图片张数、视频秒数、分辨率或任务 credits 收费。

**缓存也要拆成四类**：模型内部 KV cache、厂商 prompt/context caching、媒体文件/embedding 缓存、最终生成结果缓存。只有前两类通常直接影响 LLM API 的 token 账单；媒体 CDN 缓存主要省上传和预处理，结果缓存主要省重复推理，三者不能混称为“缓存命中”。

## Quicknotes 主题对应

```text

多模态模型是否涉及缓存命中的阶梯价格？
```

归档位置是 `My Notes/LLM/Agent Framework/`，因为它讨论的是 agent 接入不同模型/媒体 API 时的运行时和成本架构，而不是某个基础模型的训练细节。

## 不同模态到底在为什么付费

| 模态 | 输入/输出的实际计算对象 | 常见计费单位 | 主要成本驱动 |
|---|---|---|---|
| 文本理解/生成 | token 序列 | 输入 token、输出 token | Transformer 层数、序列长度、生成长度 |
| 图像理解 | 图像 patch/视觉 token + 文本 token | 输入视觉 token 或按图片/分辨率折算 | 分辨率、patch 数、视觉编码器、上下文长度 |
| 音频理解 | 音频帧/语音 token，可能先 ASR | 音频秒数、音频 token、转写 token | 时长、采样率、声学编码和语言模型处理 |
| 视频理解 | 抽帧后的图像 token + 音频 token + 文本 token | 视频秒数、帧数、视频 token | 时长、帧率、分辨率、音频轨道、长上下文 |
| 图像生成 | latent/image diffusion 或 flow matching steps | 图片张数、尺寸、质量/风格档位 | 分辨率、采样步数、模型大小、生成 batch |
| 视频生成 | 空间×时间 latent 生成 | 视频秒数、分辨率、帧率、生成模式 | 帧数、空间分辨率、时序 latent、采样步数、后处理 |
| 音频/音乐生成 | 声学 latent / codec token | 音频秒数、生成次数或套餐 credits | 时长、采样率、声道、模型和后处理 |

因此，“多模态模型价格更贵”可能来自完全不同的原因：

1. 理解类请求把媒体编码成更多 token，输入量增加；
2. 生成类请求需要运行专门的高成本 decoder/diffusion/flow 模型；
3. 生成结果还包含存储、转码、内容安全和 CDN 交付成本；
4. 服务商往往把 GPU 队列、分辨率和时延 SLA 封装成多个商业档位。

## 标准文本 LLM 的典型计费

文本 LLM 一般可以抽象成：

```text
总价 = 输入 token × 输入单价
     + cache hit token × 缓存单价
     + 输出 token × 输出单价
     + 工具/搜索/推理附加费（如果有）
```

这里的输入 token 主要是 system prompt、用户消息、历史对话、工具 schema 和检索结果；输出 token 是模型生成的回答、tool call 或 reasoning token。不同厂商会把 reasoning token 计入输出，也有厂商按内部模型档位另计，不能只比较公开的“output token 单价”。

文本输入特别适合 prompt caching，因为长前缀通常可以稳定复用：system prompt、工具定义、长文档和固定 few-shot 示例都可以放在请求前缀。缓存一般要求前缀完全一致或按厂商规则匹配，动态内容放在后面更容易命中。

## 多模态理解的计费原理

### 图像理解：图片不是“一个输入 token”

典型流程是：

```text
图片 → resize/patch → vision encoder → visual embeddings/tokens
     + 文本 token → multimodal transformer → 文本输出
```

同一张图片的成本会随以下因素变化：

- 分辨率越高，patch 数通常越多；
- high-detail 模式可能生成更多视觉 token；
- 多张图片会累加视觉 token；
- 图片可能先被缩放、裁剪或转成多视图；
- 视觉 token 与文本 token 共同占用上下文窗口。

因此某些 API 按视觉 token 收费，某些 API 按图片尺寸档位折算，不能从“图片数量”推断所有厂商的价格。

### 视频理解：通常是采样，而不是把每一帧都完整送入模型

常见流程：

```text
视频 → 抽帧/压缩 → 图像视觉 token
     + 音频抽取 → 音频/ASR token
     + 文本问题 → multimodal transformer → 文本输出
```

视频成本与时长强相关，但还取决于：抽帧策略、fps、关键帧密度、分辨率、是否保留音频、是否需要长视频记忆。服务商可能对同一个视频提供“低采样/高采样”两档，或者直接按秒计费。

### 音频理解：可以是 ASR，也可以是原生音频模型

- **ASR pipeline**：音频先转文字，再用文本 LLM；价格可能是音频分钟数 + 文本 token；
- **原生音频模型**：音频 codec/声学 token 直接进入模型；价格可能仍以秒数或音频 token 计；
- **语音对话**：还要计算实时双向流、缓存的会话上下文和 TTS 输出。

同样一段音频，走“转写后文本 LLM”和“原生音频推理”是两种成本结构，不能只看模型名字。

## 图像/视频/音频生成为什么不直接按 token 收费

生成模型的 prompt 可能按 token 收费，但真正昂贵的部分通常是输出生成：

```text
文本 prompt → text encoder/LLM
           → latent/噪声初始化
           → 多轮 denoise/flow steps
           → VAE decode / 视频后处理 / 音频 codec
```

对于视频，粗略成本可理解为：

```text
成本 ≈ 空间 latent 数 × 时间 latent 数 × 采样步数 × 模型计算量
```

视频从 5 秒变成 10 秒，不只是多输出一段文本，而是增加时序 latent 和生成计算；从 720p 变成 1080p，也会显著增加空间计算。因此按“每秒 + 分辨率 + 质量档位”收费，比按输出 token 更接近服务商实际成本。

输出缓存也更难直接复用：

- 同一个 prompt 可能因为随机 seed 产生不同结果；
- 用户常常希望“同 prompt 重新生成”，这不是缓存命中，而是重新采样；
- 参考图、mask、风格、seed、模型版本、审核策略任何一个变化都可能使结果失效；
- 视频结果还带有很大的对象存储和 CDN 成本。

因此生成 API 有时会提供“任务 id / 结果 URL / 过期时间”，但这通常是异步任务追踪或对象存储复用，不等于下一次相同请求会免费复用生成计算。

## 缓存的四个层次

### 1. 模型内部 KV cache

Transformer 在生成第 n 个 token 时，保留前面 token 的 key/value，避免每一步重新计算历史上下文。它是推理引擎的内部优化：

- 通常不直接暴露给 API 用户；
- 通常不等于账单上的 prompt cache；
- 连接断开、请求结束或换实例后可能丢失；
- 主要降低服务商延迟和算力，不一定自动转化为用户折扣。

### 2. Provider prompt/context cache

厂商把稳定的输入前缀缓存起来，下次请求复用预计算结果，直接按 cache-read 或 cached-input 单价收费。典型适合：

- 长 system prompt；
- 工具定义；
- 大型固定文档；
- 长视频/图片上下文在同一会话中的重复引用（是否支持取决于厂商）。

常见限制：最小 token 数、TTL、精确前缀匹配、缓存 key、模型版本绑定和显式 cache creation。缓存命中通常只减少输入处理费，不会减少输出 token 或生成视频的主成本。

Google Gemini 的官方文档还说明，Gemini 2.5 及更新模型默认支持 implicit caching，并会在命中时自动传递成本节省；这说明“是否需要显式创建 cache”是 provider-specific 的，不能假设所有 API 都一样。

### 3. 媒体资产/预处理缓存

这是应用或平台层的缓存：

- 图片 URL、视频文件、音频文件的对象存储/CDN；
- 文件 hash → 已解析视觉 token/embedding/ASR transcript；
- 视频抽帧结果、缩略图、OCR、字幕和 scene segmentation；
- 多个 agent 共享同一份上传素材。

它可以显著减少重复上传和预处理，但不代表模型一定免掉 transformer 推理，也不代表 provider 会把它计为 prompt-cache hit。除非 API 明确支持持久化文件引用或 context cache，否则这是开发者自己维护的缓存。

### 4. 最终结果缓存

应用可以用请求规范化后的 hash 缓存最终文本、图片或视频结果：

```text
cache_key = hash(model, prompt, inputs, seed, resolution, duration,
                 sampler, safety_policy, version)
```

这适合完全相同且可接受复用结果的任务，例如批量缩略图、固定模板视频或相同 OCR 请求。它是“业务结果缓存”，不是模型内部的缓存；如果用户要求随机新图，必须显式绕过它。

## 多模态到底能不能缓存

### 图像理解：可以，但通常是缓存视觉前缀或预处理结果

如果同一图片在多个问题中重复出现，理论上可以缓存：

1. 图片文件和规范化版本；
2. vision encoder 输出；
3. 图片对应的视觉 token；
4. 包含图片的 prompt 前缀的 KV/context cache。

但四者是否可用分别由应用、推理引擎和 API provider 决定。最稳妥的应用级策略是自己按图片内容 hash 缓存 OCR、caption、embedding 和预处理结果；不要默认 provider 会按“同一 URL”识别为同一图片。

### 视频理解：部分可缓存，但收益与一致性更复杂

可以缓存抽帧、音频转写、字幕、shot boundary、视觉 embedding 等中间产物。完整 transformer 上下文是否可缓存，则取决于：

- 采样参数是否一致；
- 视频规范化版本是否一致；
- provider 是否支持 multimodal context cache；
- cache TTL 和上下文长度限制；
- 后续问题是否只是追加文本，还是改变了视频处理方式。

对 agent 开发者而言，把长视频先处理成可复用的“媒体索引 + 结构化摘要”通常比每次重新发送整段视频更可控。

### 图像/视频生成：输入 prompt 可以缓存，主生成结果通常不能自动缓存

固定的 system prompt、风格说明、参考素材描述可以进入 prompt cache；但真正的视频 latent 采样通常需要重新计算。应用可以缓存完全相同请求的最终结果，但那是业务层去重，不是模型天然的 cache hit。

### 音频生成：文本/声音参考可以缓存，随机声学生成通常不缓存

voice profile、speaker embedding、固定音乐风格和文本前缀可以缓存；不同 seed、时长、节拍、情绪和采样参数通常意味着重新生成。

## Seedance 最新价格与策略

### 先区分版本和平台

截至本次调研（2026-08-05），公开资料中出现 Seedance 2.0 和 Seedance 2.5 的不同平台信息。中国区火山方舟、海外 BytePlus/Dreamina、产品套餐和 API 可能不是同一价格表，必须同时记录**平台、区域、模型版本和生效时间**。

### Seedance 2.0：按可计费 token，而不是简单按视频秒数

火山方舟官方模型价格页对应的公开信息是：

| 模式 | 价格 |
|---|---:|
| 纯视频生成（无视频输入） | **¥46 / 百万可计费 token** |
| 视频编辑/参考视频模式 | **¥28 / 百万可计费 token** |

这里的 token 不是用户看到的文字 token，而是平台对视频生成任务的计费 token/媒体处理量。视频输入模式价格更低的公开价差，不能简单解释成“输入视频更便宜”；它可能反映不同任务模式、套餐策略或阶段性定价，实际调用仍应以当前控制台返回的 usage 和计费页为准。

### Seedance 2.5：价格信息需要标记为平台/上线状态敏感

调研结果出现过以下公开数字：无视频输入约 **¥70 / 百万可计费 token**，有视频输入约 **¥42 / 百万可计费 token**；也有海外平台以美元换算或按模型 ID 单独展示的价格。由于不同结果存在 API 上线时间和区域差异，笔记不把它们合并成单一全球价格。

对开发者来说，Seedance 的定价策略重点是：

- 计费对象是视频任务的可计费 token/媒体复杂度，而不是纯文本输入 token；
- 参考视频、图像和文本 prompt 可能进入同一次任务的综合计费；
- 产品会员/资源包/Agent Plan 与 API 按量计费不是同一合同；
- 需要按模型 ID、平台区域、输入模式、输出分辨率/时长读取实时价格；
- 当前公开资料没有显示一个类似 Anthropic/OpenAI 文本 prompt cache 的通用 Seedance 缓存折扣阶梯，不能假设重复参考素材会自动降低主生成费用。

这里的 **MiniMax-H3 是视频生成模型**，不是 MiniMax M 系列文本模型，也不是 Hailuo 系列的别名。官方 API pricing 页给出的按量价格：

| 输出分辨率 | 计费 |
|---|---:|
| 2K | **$0.13 / 秒** |
| 768P | **$0.08 / 秒** |

### 输入素材

| 素材 | 规则 |
|---|---|
| 音频 | 免费 |
| 图片 | 前 5 张免费，之后 **$0.04 / 张** |
| 视频 | 按输入视频时长和输出分辨率对应的秒单价计费 |

### 其他 H3 相关任务

## 给 Agent 开发者的成本模型

多模态 agent 不应只用“LLM input/output token price”估算总成本，应该按任务拆成：

```text
总成本 = 文本模型调用
       + 视觉/音频/视频理解预处理
       + 输入媒体计费
       + 生成媒体计费（秒/张/分辨率/质量）
       + 工具/API 调用
       + 存储/CDN/转码
       + 重试和候选采样
       - provider prompt-cache 节省
       - 应用层媒体/结果缓存节省
```

推荐的工程策略：

1. **先做媒体 fingerprint**：同一素材只上传、抽帧、ASR、OCR 一次；
2. **缓存中间产物**：字幕、shot、embedding、caption 和结构化 metadata 比缓存整段模型上下文更稳定；
3. **把生成任务参数完整纳入 cache key**：模型、版本、seed、分辨率、时长、参考素材、声音、审核策略都不能漏；
4. **区分 preview 和 final**：先用低分辨率/短时长生成预览，确认后再调用高价 final；
5. **限制候选数和重试**：生成模型的成本常由“多候选 + 失败重试”放大，而不是单次 prompt；
6. **记录每个 node 的成本**：在 graph/agent state 中记录输入媒体、输入输出 token、cache hit、生成秒数、分辨率、重试次数和最终结果；
7. **不要默认缓存命中**：每个 provider 都要用真实 usage 字段验证是否 hit，以及命中后究竟减免哪一部分；
8. **长视频先建立媒体索引**：后续问题通过索引和局部片段处理，避免每轮发送完整视频；
9. **最终生成结果要明确复用策略**：用户要求“再生成一个”时绕过 result cache，用户要求“继续编辑”时复用原始素材和中间状态。
